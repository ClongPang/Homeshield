# 家中盾——技术选型

> 本文记录影响整体架构的技术决策及其适用边界。新增选型时补充决策依据、替代方案和演进条件。

## 控制台实时告警：SSE

**状态：已采用**

**范围：** 家人控制台打开期间的高危告警增量更新。

### 决策

采用浏览器原生 `EventSource` 接收 SSE，服务端通过 FastAPI `StreamingResponse` 推送告警事件。浏览器通过普通 HTTP API 获取告警历史、提交查询和反馈；SSE 只负责服务端向控制台推送新增告警。

微信模板消息仍负责控制台未打开时的高危通知。SSE 不承担离线推送职责。

### 选择依据

- 告警流是单向的：服务端有新告警时通知浏览器，浏览器不需要在同一条连接上持续发送业务消息。
- `EventSource` 是浏览器原生接口，连接中断后会自动尝试重连，适合控制台的增量事件流。
- 查询、纠正和成员管理本来就是请求/响应操作，继续走 HTTP API 即可，无须让所有通信都进入长连接协议。
- 普通轮询也能取到告警，但需要周期性发请求，并在两次轮询之间产生延迟。SSE 在服务端有事件时再发送。

### 替代方案

| 方案 | 适用情况 | 本项目的判断 |
|---|---|---|
| WebSocket | 浏览器和服务端都需要在长连接上频繁发送消息，例如实时聊天、协作编辑 | 当前告警只需服务端推送，双向能力暂时用不上 |
| 定时轮询 | 更新不频繁，允许一定延迟，且希望不维护长连接 | 可以作为简单替代，但控制台告警会有轮询间隔造成的延迟和空请求 |
| SSE | 服务端向打开的网页持续推送事件，客户端业务操作仍走 HTTP | 符合当前控制台告警模式 |

### 实现与可靠性边界

- 控制台先请求告警历史，再通过 SSE 接收新增告警；前端按 `verdict_id` 去重，避免历史请求和实时事件重复展示。
- 每个 worker 保留本地 `AlertBroker`。verdict 事务提交时以 `pg_notify('verdict_completed', ...)` 广播主键；每个 worker 通过专用连接 `LISTEN` 后重读业务行并走同一 `AlertRouter`。本地 EventBus 与数据库通知可能触发双消费，`alert(verdict_id, relation_id)` 的唯一约束和 `ON CONFLICT` 保证落表幂等；SSE 载荷按 verdict 去重。
- Postgres NOTIFY 只作即时广播提示，不是持久队列。断线期间错过的事件不自动重放；告警历史仍可经 API 读取。
- SSE 连接本身不保证微信模板消息送达，也不替代告警落库。

### 演进条件

出现浏览器与服务端需要双向实时交互的产品需求时，再评估 WebSocket。需要多进程/多实例广播或断线补发保证时，先扩展事件分发与持久化能力；只有实际需求要求双向通信时才更换传输协议。

## 运行数据：Postgres 16

**状态：已采用**

服务运行数据统一存入 Postgres 16；`DATABASE_URL` 是唯一运行时连接配置。`psycopg` async pool 每 worker 最多 10 个连接，语句超时 5 秒，会话时区 UTC。时间列使用 `timestamptz`，判定快照使用 `jsonb`，唯一约束、部分索引与事务承担并发不变式。离线素材构建器 `kbbuild` 仍使用 SQLite，与在线服务隔离。

开发环境由 `docker-compose.yml` 提供本机 Postgres，默认 5432 仅绑定 `127.0.0.1`。SQLite 迁移只支持当前单向关系模型 schema；不把旧群模型转换成关系数据。迁移和回滚按 [`deploy/postgres-cutover.md`](../deploy/postgres-cutover.md) 执行。备份使用 `scripts/backup_postgres.sh`，恢复目标必须是空库并由 `scripts/restore_postgres.sh` 检查。
