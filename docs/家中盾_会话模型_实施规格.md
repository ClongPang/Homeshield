# 家中盾 会话模型 实施规格

> 版本:v1.1 | 2026-09-27 | 状态:**待开发**
> 读者:开发与测试。设计依据:《家中盾_会话边界_问题记录》v1.5(§6 方案方向、§6.10 判据);状态同步至《架构技术》(交付时 v2.25+)。
> 判定契约:v1 的 judge 只看本条消息,前情只参与判定后的确定性下限和受控依据;`notifier.py`/`events.py`/`retrieval.py`/`annotate.py` 不动;`JudgeInput` 结构不变;每条消息独立 intake、独立 verdict、msg_id 幂等语义不变。

## 1. 目标与不变式

**目标**:查询者的多条消息按时间连成"案件"与"前情",判定跨消息渐进式骗术(杀猪盘/刷单/公检法类);同时把"谢谢"类消息从判定链路摘出,停止浪费回复额度与统计。

五条不变式,所有实现决策用它裁决:

| # | 不变式 | 含义与可验证表述 |
|---|---|---|
| I1 | 判定粒度逐条 | 每条查询消息独立 intake/独立 verdict/msg_id 幂等;`PipelineResult` 结构不变;新增持久化仅为 `incident` 分区、`query.transcript` 回写与 `verdict.context_snapshot`;ack 不产生 verdict |
| I2 | 失败退向基线 | 供给异常、当前 query 分区失败或开关关闭时,不使用任何前情;本条照常判定,结果与无供给模式等价;转写回写失败也不改变判定。**分区失败不挡本条判定** |
| I3 | 只抬不下 | judge 只收到本条文本、特征与案例,调用一次;前情仅在 judge 返回后经确定性跨条下限抬升最终级别,`final_level = max_level(self_floor,cross_floor,judge_level)`。旧 verdict 的 `level`/`reason` 不回流,有供给级别因此不低于无供给级别 |
| I4 | 前情依据受控 | 旧结论和旧消息原文不进入 judge 或回复生成器;仅当跨条下限**实际抬升级别**时,代码生成一句不含原文摘录的依据(如"前情有保密要求,本条又要求转账"),并注明跨消息来源。`reply.py` 需支持此受控依据;`add_delivery_notice` 不变 |
| I5 | 分诊只降级不跳过 | 分诊只有两种非判定出路:命令类(纯 DB+被动回复)、确认类(落 `kind='ack'`+被动回复,不跑管线);**任何无法确定类别的消息(含图片、含 URL、超长文本)一律进完整判定**;确认类与查询类永远有回复(被动回复已在 5s 窗口发出) |

**反屎山纪律**:不建通用 session/工作区框架;不建跨用户会话(骗子分别联系两名家庭成员不属本规格);v1 不上向量检索与 LLM 语义判定供给(留 v2 独立预注册);不写旧库迁移层(dev 库重建);不做案件聚合 UI/周报(消费端另行立项);每个新配置项必须能一句话说清"调它会改变什么行为"。

## 2. 范围

### 2.1 做(P1→P5,五个切片,每片独立收口)

1. **P1 数据底座**:`incident` 表、`query.kind/incident_id` 列 + `IncidentRepo`;schema 先具备 ack 落库与重置能力,判定行为不变;
2. **P2 分诊、命令与分区**:新增 `core/triage.py`(纯函数);微信回调同步分诊分支("新的"重置、确认类免判定);query 落库时分区;`messages.py` 新文案;web `/api/query` 响应加 `kind` 字段;CLI `incident` 子命令;
3. **P3 转写落库**:`query.transcript` 列;管线阶段 1 判定后回写;
4. **P4 供给 v1(supply-as-features)**:`Repo.supply_context` 选取;跨消息合成特征(escalation 跨消息、isolation/transfer 跨条下限);`Feature.origin` 字段;受控回复依据;`verdict.context_snapshot` 快照;`PipelineConfig.supply_features` 开关 + `PIPELINE_VERSION→1.2.0`;
5. **P5 评测与判据**:`kbcli export-cross-message`(分层样本导出);`run_eval --supply` 双跑对比;五项判据报告(`docs/reports/session_report.md`)。判据通过后单独提交翻转 `supply_features` 默认为 True,并递增行为版本。

**P1–P3 上线时 `supply_features=False`:原有查询的判定算法不变;确认类不再判定。**

### 2.2 不做(明确出范围)

| 不做 | 原因 |
|---|---|
| v2 供给原文进 prompt(supply-as-context) | 增量价值在恐吓弧类,须独立预注册判据(《问题记录》§6.10);本规格只留 `context_snapshot` 的 v2 版本号字段 |
| 案件聚合消费端(周报/UI/案件页) | 分区先落库后消费;无消费端不影响判定正确性 |
| 跨家族/跨用户会话 | user 键天然切不开,真盲区,如实记录于《问题记录》§7 |
| 检索式/语义式供给 | 已知盲区("还是那个平台"),判据跑批后若召回不足再立项 |
| 旧库迁移兼容层 | dev 库重建;生产部署前仅 init-db 建新 schema |
| console.html / alert.html / join.html 改动 | web 端仅 `/api/query` 响应加 `kind` 字段,前端对未知字段免疫,零改动 |

## 3. 数据模型(DDL delta,一次性重建 dev 库)

在 `src/homeshield/core/db.py` 的 schema 中新增/修改(基础表以当前代码为准):

```sql
CREATE TABLE IF NOT EXISTS incident(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES user(id),
    opened_at INTEGER NOT NULL,          -- Unix 秒
    last_query_at INTEGER NOT NULL,      -- 最后一次 kind='query' 落库时间
    closed_at INTEGER,                   -- NULL=开放
    close_reason TEXT CHECK(close_reason IN ('timeout','explicit','manual'))
);
-- 并发兜底:同一用户至多一个开放案件(与 uq_active_member 同构)
CREATE UNIQUE INDEX IF NOT EXISTS uq_open_incident
    ON incident(user_id) WHERE closed_at IS NULL;

CREATE TABLE IF NOT EXISTS query(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES user(id),
    content_type TEXT NOT NULL CHECK(content_type IN ('text','url','image')),
    content TEXT NOT NULL,
    msg_id TEXT,
    created_at INTEGER NOT NULL,
    incident_id INTEGER REFERENCES incident(id),        -- 新增;可空:分区失败不挡判定
    transcript TEXT,                                    -- 新增;图片转写文本(判定后回写),可空
    kind TEXT NOT NULL DEFAULT 'query' CHECK(kind IN ('query','ack'))  -- 新增
);
CREATE INDEX IF NOT EXISTS ix_query_user_time ON query(user_id,created_at);
CREATE INDEX IF NOT EXISTS ix_query_incident ON query(incident_id);

CREATE TABLE IF NOT EXISTS verdict(
    -- 现有列不变,末尾新增一列:
    context_snapshot TEXT               -- 新增;供给快照 JSON,可空;NULL=无供给
);
```

约定:`ack` 行 `incident_id` 恒为 NULL(确认消息不参与分区,详见 §4.2);`transcript` 仅 `content_type='image'` 时写入;`context_snapshot` 结构见 §4.6。

## 4. 领域规则(精确算法定义,实现与测试以此为准)

### 4.1 分诊与命令:纯函数 `core/triage.py`

```python
RESET_COMMANDS: frozenset[str] = frozenset({"新的", "新问题"})
ACK_TEXTS: frozenset[str] = frozenset({
    "谢谢", "多谢", "辛苦了", "好的", "好", "嗯", "嗯嗯", "哦",
    "知道了", "收到", "收到了", "明白", "明白了", "了解", "好滴", "好嘞",
})
ACK_ASCII: frozenset[str] = frozenset({"ok", "okay"})   # strip 后 lower 比较

def classify(text: str) -> str:
    """返回 'reset' | 'ack' | 'query'。纯函数,无 IO。"""
```

`classify` 判定顺序(**即代码顺序,不得重排**):

1. `t = text.strip()`;若 `t in RESET_COMMANDS` → `'reset'`;
2. 若 `t.lower() in ACK_ASCII` 或 `t in ACK_TEXTS` → 候选 ack,继续第 3 步校验;否则 → `'query'`;
3. ack 校验(全部满足才返回 `'ack'`,任一不满足返回 `'query'`):无 URL 命中(`intake._URL_RE` 复用);`len(t) <= 20`(固定护栏,词表精确匹配已更严格)。

边界由词表精确性保证:"好的，那我转了""谢谢，但是有个事"因非精确匹配返回 `'query'`,进完整判定。**图片与 URL 类型消息不经过本函数的 ack 分支**(调用方仅对 `content_type='text'` 调用;URL 类型一律 `'query'`)。

**优先级**(写在 `core/triage.py` 模块 docstring):未绑定引导 → 群命令(开通/绑定/我的群/退出/解散,现有 `_handle_membership_command`)→ 微信 `reset` → `ack` → 完整判定。网页 `/api/query` 只处理 ack/query,`"新的"` 按普通查询处理;网页无重置按钮是本期接受的交互缺口。

### 4.2 案件分区算法

**分区只对 `kind='query'` 的行发生;`ack` 行不分区、不续命**(`last_query_at` 不更新)。时间间隔一律以 `query.created_at` 对 `incident.last_query_at` 计算。

`VerificationService.verify` 先以同一纯函数分诊(网页的 `reset` 归为 query;微信的 `reset` 已由回调命令路径处理),再把 `kind` 传给 `ingest` 原子写入(幂等仍由 `msg_id` 唯一索引保证);`kind='query'` 的消息在 `ingest` 成功后、`pipeline.run` 前执行分区。微信入口为选择被动回复先运行同一纯函数,后台写入时再次运行不会改变分类。

```text
attach_query_to_incident(query_id, user_id, now):
    1. inc = SELECT * FROM incident WHERE user_id=? AND closed_at IS NULL
    2. 若 inc 存在:
         若 now - inc.last_query_at <= INCIDENT_IDLE_SECONDS:
             UPDATE incident SET last_query_at=now WHERE id=inc.id
             UPDATE query SET incident_id=inc.id WHERE id=query_id; return
         否则: UPDATE incident SET closed_at=now, close_reason='timeout' WHERE id=inc.id
    3. INSERT INTO incident(user_id, opened_at=now, last_query_at=now)
       —— uq_open_incident 冲突(IntegrityError)时回到第 1 步重试一次(并发窗口兜底)
    4. UPDATE query SET incident_id=新案 id WHERE id=query_id
```

- **原子性与失败语义**:步骤 1–4 在同一写锁和数据库事务内执行,任一步骤失败整段回滚(唯一索引冲突的那一次按步骤 3 重试),随后仅 `logger.warning`,不抛出;`query.incident_id` 保持 NULL,本条仍判定但不使用前情(I2)。
- **显式重置**(仅微信命令路径):`close_open_incident(user_id, reason='explicit')` 关闭当前开放案(无开放案则幂等返回);不建新案;不落 query;不判定。被动回复 `SESSION_RESET_REPLY`。
- **旧数据**:存量 query 行 `incident_id=NULL`,永不回填;它们只能在 7 天窗内通过账号/链接强特征匹配成为候选。当前新 query 必须分区成功才启用供给。

### 4.3 供给选取算法(v1,supply-as-features)

入口 `Pipeline._supply(message, query_id) -> list[SupplyItem]`,仅在 `PipelineConfig.supply_features=True` **且当前 query.incident_id 非空**时调用。`SupplyItem = dataclass(query_id: int, created_at: int, text: str, specs: list[FeatureSpec])`。当前图片须先转写,再用转写文本提取本条强特征。

**候选池 SQL**(一次查询,`Repo.supply_context`):
```sql
SELECT id, content_type, content, transcript, created_at, incident_id
FROM query
WHERE user_id=? AND kind='query' AND id<? AND created_at >= ?
ORDER BY created_at DESC LIMIT 200
```
参数:`user_id`=当前查询者,`id<` 当前 query_id(排除自身),`created_at >= now - SUPPLY_WINDOW_SECONDS`。

**候选文本**:`content_type='image'` 取 `transcript`(为空则文本按空串,该条无特征但保留同案归属);`text/url` 取 `content`。

**入选规则**(对候选池按时间**升序**遍历后统一截断):
1. **同案入选**:`incident_id` 非空且等于当前 query 的 `incident_id`(当前 query 分区失败时整个供给退向基线,不再跨案匹配);
2. **跨案强特征匹配**:提取当前消息强特征值集合 `S_cur`(对当前文本跑 `extract_rule_features`,取 `type in {'account','url'}` 的 `value`,归一化:去所有空白、URL 去尾斜杠并整体 lower);候选文本同法提取得 `S_i`;`S_cur ∩ S_i ≠ ∅` 即入选,匹配上的值记入快照 `matched_values`;
3. 按时间升序排序、按 query_id 去重,**保留最近 `SUPPLY_MAX_ITEMS`(默认 10)条**,更旧的丢弃;
4. 对每条入选候选跑 `extract_rule_features(候选文本)` 得 `specs`(cache 无需,regex 代价可忽略),装配为 `SupplyItem`。

**失败语义**:`supply_context` 抛出任何异常 → `logger.warning` + 返回空列表,判定与无供给模式完全一致(I2)。

### 4.4 跨消息合成特征与单向下限(v1)

记当前消息规则特征(含逐轮 turn)为 `cur_specs`,供给候选按时间升序为 `P1..Pn`(时间上均早于当前消息)。本条原始特征照常进入 judge;候选原始特征只供规则计算,**不进入 judge 或回复**。judge 返回后再追加以下合成特征到持久化 features,计算跨条下限;合成特征也不重新送入 judge。

**S1 跨消息升级特征**:构造伪轮次序列——`Pi` 的全部 specs 标 `turn=i`(整条候选占一个轮次号),当前消息轮次顺延为 `n+1..n+k`;复用 `detect_escalation_feature` 的机制映射(铺垫类 `identity/bait/fear/emotion`,索取类 `money/sensitive/control`)。**索取必须出现在本条**,铺垫必须至少有一条来自前情,避免旧消息独自形成升级而让本条无关消息受罚。触发时 `cross_floor` 至少为 `suspicious`;仅有"铺垫→索取"不足以强制高危。产出:

```python
FeatureSpec(type="escalation", source="rule", confidence=8, turn=0,
            value=f"约{age}前的消息已建立铺垫(身份/利益/恐吓/情感),本条出现索取(跨消息渐进话术)",
            evidence_span="")
```
其中 `{age}` 指铺垫轮所在候选距当前消息的时距,格式:`<60min` → `N分钟`;`<24h` → `N小时`;否则 `N天`。**注**:铺垫类机制含 `fear`,故公检法类恐吓弧(前情假通缉令→本条转账)可由 S1 抬到至少 suspicious;`isolation` 不属铺垫类,恐吓式保密话术由 S2 的高危下限兜底。

**S2 跨条高危下限**:仅当**前情命中 isolation 且本条命中 transfer**、本条自身尚未达到 `dangerous` 时,`cross_floor=dangerous`;前情里的 isolation+transfer **不能单独抬高后续无关消息**。"前情 transfer + 本条 isolation"本期不强制高危,牺牲这一路径的部分召回以降低误报;留在对照样本中观察。为前情贡献的 isolation 合成一条证据特征:

```python
FeatureSpec(type="isolation", source="rule", confidence=5, turn=0,
            value="前情有保密要求", evidence_span="")
```
作用:作为最终判定的跨消息依据。只在 `cross_floor` **实际抬高**最终等级时,将造成抬升的合成特征(S1 或 S2)及本条索取/transfer 特征 ID 加入 `cited_ids`,并用这些 ID 生成确定性的 `verdict.reason`;不得依赖现有的"所有 isolation/transfer 一律强制引用"逻辑(会误引无关证据)。

**落位与编号**:judge 输入维持 `assign_feature_ids(rule_specs + sup)`;judge 返回后给合成特征继续分配 ID,仅供最终 verdict/快照/受控依据使用,不回传 judge。`origin="prior"`;`turn=None`(经 `turn=0` 归一);S1+S2 至多 2 条。`self_floor=get_rule_risk_floor(cur_specs)`,`final_level=max_level(judge_level,self_floor,cross_floor)`。**retrieval_query 仍只用当前消息特征**。S1 单独触发只升至 `suspicious`;S2 可升至 `dangerous`。这样只抬不下是程序不变式,不依赖提示词或样本碰运气。

**受控回复**:只有最终等级被 `cross_floor` 抬升时,调用 `ReplyGenerator.generate` 传 `basis_override`(代码从 S1/S2 类型生成,不得拼接旧消息原文或合成特征的 `value`);生成器用该句作为【依据】,建议仍只依据本条特征/案例生成。未抬升时沿用现有回复路径。此举牺牲 v1 中对历史细节的解释,换取不误引旧截图原文;旧 verdict 结论始终不进入回复。

### 4.5 转写回写

`Pipeline._extract_message_text` 成功且 `content_type=='image'` 时,执行 `UPDATE query SET transcript=? WHERE id=?`(经 `QueryRepo.update_transcript`);失败仅 `logger.warning`,不影响判定。文本/url 类型不回写。

### 4.6 快照与配置

**`verdict.context_snapshot` JSON schema(v1)**:
```json
{"v": 1,
 "prior": [{"query_id": 123, "age_seconds": 259200, "excerpt": "≤200字",
            "source": "feature_match", "matched_values": ["6222..."]}],
 "synthetic_ids": ["F07", "F08"],
 "floor_level": "dangerous"}
```
`source` 可为 `same_incident` 或 `feature_match`;前者 `matched_values=[]`。无供给时写 NULL。快照在 `_persist_verdict_and_publish_event` 内、`VerdictRepo.insert` 前装配,随 verdict 同事务落库。

**配置项**(`Settings` 新增,全部有默认值,不配置即工作):

| Settings 字段 | 环境变量 | 默认 | 调它改变什么 |
|---|---|---|---|
| `incident_idle_seconds` | `INCIDENT_IDLE_SECONDS` | `21600`(6h) | 同用户两条查询并入同一案件的间隔上限 |
| `supply_window_seconds` | `SUPPLY_WINDOW_SECONDS` | `604800`(7d) | 跨案供给候选的时间窗 |
| `supply_max_items` | `SUPPLY_MAX_ITEMS` | `10` | 单次判定的供给候选上限 |

`PipelineConfig` 新增 `supply_features: bool = False`;**新增该字段时同步 `PIPELINE_VERSION → "1.2.0"`**(词表扩充也随本次生效,见 §5);判据通过后单独提交将 `product_default` 翻为 True,并将 `PIPELINE_VERSION → "1.2.1"`。默认行为改变也须失效旧评测缓存。

## 7. 评测与判据(v1)

### 7.1 样本导出 `kbcli export-cross-message`

输出 JSONL,每行一个"跨消息弧":

```json
{"arc_id": "conv#012",
 "stratum": "trust_same_incident",
 "messages": [{"text": "...", "delay_seconds": 3600},
              {"text": "...", "delay_seconds": 86400}],
 "final_label": "scam", "scam_type": "romance_pigbutchering", "source": "adapted:fraud-r1"}
```
`stratum` 另可取 `trust_linked`、`trust_unlinked`、`fear`、`overwindow`、`mismerge_benign`、`mismerge_risky`。

- **trust 同案层**:52 条会话体样本(现有 `export-conversations` 数据源)逐条拆为 3–4 条消息,相邻 delay ≤6h,检验 S1 的实际增益;
- **trust 跨案有标识层**:另取 ≥12 条,相邻 delay 为 1–3 天,前后重复真实可抽取的同一账号或链接,检验强特征跨案供给;
- **trust 跨案无标识层**:另取 ≥12 条,相邻 delay 为 1–3 天,只有"他又让我转账"一类回指,无重复账号/链接;作为已知盲区单独报告,不得混入可覆盖层稀释分母,也不得声称 v1 解决;
- **fear 层**:新增 ≥12 条公检法/退款类同日多步弧(delay 分钟级),人工编写并过审;
- **overwindow 层**:≥8 条,首条 delay > `SUPPLY_WINDOW_SECONDS`,验证"窗口外不供给,单条判定不回退为漏报"(仅回归语义,不计入 Recall 判据);
- **误并对照**:两组各 ≥30 条 benign 当前消息:①同 user 无关 benign 前情;②同 user 带 isolation/transfer 的风险前情,其中必须覆盖"前情已同时命中两者,本条无风险特征"与"前情隔离+本条良性转账"。delay 均在 6h 内,检验时间分区误并及重复高危告警。

### 7.2 五项判据(预注册,跑批报告 `docs/reports/session_report.md`)

1. **Recall 与有效收益**:可覆盖的 trust 同案/跨案有标识层 + fear 层,每条弧最终消息级别 ≥ 单条基线(同批样本 `--supply off` 对照),弧级 Recall 不低于基线;其中至少 1 条基线漏报被纠正且无新增漏报,并单列供给命中率。若基线没有漏报或改进为零,不得以"不回归"冒充有效收益,默认仍关,待真实回流或新样本验证。trust 跨案无标识层只报告盲区,不计入 v1 增益门;
2. **FPR**:误并对照层 FPR 与 FPR(strict) 均不高于基线;
3. **只抬不下**:全样本断言 `level(supply=on) ≥ level(supply=off)`(允许相等);
4. **故障注入**:固定同一确定性的 judge/reply 测试替身,monkeypatch `supply_context` 抛异常 → JudgeInput 与 `--supply off` 相同,判定语义字段(`level/cited_ids/reason/reply`)一致;query/verdict ID、时间和耗时不作跨运行等值比较;
5. **预算**:llm 模式 p95 延迟增量 ≤ 50ms(mock 模式不增),单次判定 features 数量 ≤ 现状 + 2(1 条 escalation + 1 条 isolation 合成),judge 调用次数不增加。

任一判据不过:`supply_features` 默认保持 False,问题记录文档追加失败记录,不二次调参偷跑(重跑须改判据并注明)。

## 11. 影响范围与边界汇总

**性能边界**:每次 query 判定新增 ≤1 次 SQL 读(候选池 ≤200 行)+ ≤10 次纯 regex 抽取 + 1 次关案/续命写;p95 预算见判据⑤。**数据边界**:verdict 行新增有上限的 context_snapshot(最多 10 条×每条 200 字;UTF-8/JSON 字节数可能超过 2KB),query 行新增 transcript(图片判定后)。**行为边界**:分诊只影响 text 类;图片/URL 一律判定;`ack` 不产生告警、不进周报统计口径。**安全边界**:旧消息原文只进规则提取与快照,不进入 judge 或回复生成器;回复可在抬升时出现代码生成的抽象前情依据。**已知残留盲区**:同 user 双骗局并行靠 6h 窗切不开、跨案无强特征延续连不上、超 7 天弧不供给、跨家族不可见。

## 12. 风险与观察项

| 风险 | 概率 | 缓解 |
|---|---|---|
| 跨条下限误抬(前情良性"保密"字样 + 当前良性"转账"字样 → dangerous) | 中 | 判据②误并对照层把关;不过则 supply 默认关,侵权面为零 |
| 跨案匹配召回不足(骗子换收款账户) | 高 | 同案路径不受影响;判据①分层样本定位损失层;检索式供给另立项 |
| ack 词表误伤真求助 | 低 | 精确匹配 + ≤20 字 + 无 URL 三重约束;方向安全(误判 query 多花一次判定,不漏报) |
| 骂回复额度:ack 用户反复发确认词刷屏 | 低 | ack 落库可统计;观察项:单 user 24h ack 行数,超阈值再限频(本期不做) |
| 词表扩充改变现有样本判定(isolation 新词命中) | 确定 | 跑批对照列出受影响样本;PIPELINE_VERSION 已 bump,缓存按规失效 |

## 13. 部署注意

- 生产部署前 `init-db` 重建(新 schema 含 incident/kind/transcript/context_snapshot);无在线迁移;
