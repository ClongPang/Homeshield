# 家中盾 过程总结（面试用）

## safe 输出的产品责任问题（2026-09-26）

safe 输出本质是产品责任问题：系统说"安全"即作出担保，判错须担责；且代价不对称——误报伤体验，漏报伤信任。解法不是取消该级（全员可疑会淹没真告警），而是改"言语行为"：结论只说"未发现已知骗术的特征"，固定兜底核实建议，低置信禁止判 safe、降级"拿不准"交人工。担保变陈述，责任随口径收回。

> 落地锚点：`src/homeshield/core/reply.py`（结论行/兜底建议代码所有）｜`src/homeshield/core/judge.py` `judge_with_validation(safe_confidence_floor)`（低置信重试耗尽走 DegradeError）｜`SAFE_CONFIDENCE_FLOOR`（默认 60，仅 llm 模式，mock 置信分为合成值不参与）｜全量 93 测试通过。

## 告警链路"只推不拉"：实时推送服务了一个不存在的使用场景（2026-09-26）

高危告警 UI 原本只由 SSE 实时推送渲染——但控制台唯一现实的打开方式是"点模板消息进来"，此时触发本次告警的判定早已发布完毕，用户看到的恰是"暂无告警,等待推送"；更实质的伤害是"记录为误报"按钮只挂在实时卡片上，全家没人开着页面时纠正入口就整个丢失。"理解错用户"很少表现为做错整个系统，而是把 done-when 写在不存在的使用场景上：FR-6 验收的是"同一次运行内 SSE 送达"，而用户可感知的送达是微信震动。修法是把告警面拆成"拉取(真相之源)+ 推送(补增量)"：alert 表 join 出历史接口，控制台打开先渲染历史，SSE 只补增量，纠正按钮历史/实时两处都挂。

> 落地锚点：`src/homeshield/core/repo.py` `AlertRepo.list_for_user_group`（join verdict/query,按判定去重）｜`src/homeshield/api/groups.py` `GET /api/alerts`（响应形状对齐 SSE payload）｜`src/homeshield/web/console.html` `alertCard/loadAlerts`（合并式渲染,按 verdict_id 去重）｜《产品定位》FR-6 修订。

## 端口-适配器的最后一步是装配：接线缺失只能靠审计发现（2026-09-26）

微信模板消息的 `TemplateSender` 端口与 `WeChatChannel.send_template` 适配器都实现了、router 也留了注入点，但组合根从未把两者接起来——`AlertRouter.wechat` 恒为 None，`_spawn_wechat` 进门就 return。代码"完整"地实现了一个永远不会被调用的能力，测试全绿，因为契约测试靠手动注入 fake 才成立。教训有三：①端口/适配器/装配三件套要作为整体验收，装配本身要有专测（无凭证→None、部分凭证→关闭而非发送时失败、全凭证→注入同一实例）；②通道类应为单例——原实现每个回调请求 new 一个适配器，access_token 缓存形同虚设、httpx 客户端永不关闭；③"部分配置"要有明确语义：只配 wechat_token 时回调链路可用、模板保持关闭，而不是运行时报错。

> 落地锚点：`src/homeshield/core/deps.py` `build_deps`（wechat 单例挂 Deps + 三件套门槛注入 `router.wechat`）｜`src/homeshield/api/wechat.py`（回调改用 `deps.wechat` 共享实例）｜`tests/test_wechat_flow.py` 三个装配门槛测试 + `test_template_message_carries_console_link`（deep-link 契约）。

## elder/adult 角色退役为纠正信任位：告警受众不该由年龄决定（2026-09-26）

用户质询"为什么要有家长和子女的角色,群内人人平权不行吗"。复盘结论:角色系统把两个本应独立的策略焊死在年龄上——①告警受众(仅 adult)让"谁收到干预通知"由身份而非意愿决定;②纠正权限(elder 需确认)实为数据质量防火墙,防的是诚实误标污染回流数据,与年龄无关。修正为防护群模型:全员平权查询/收推送/看周报;`member.role` 列退役为 `member.trusted` 纠正信任位,开通创建者即群主(trusted),绑定成员默认普通,信任成员可翻转他人信任位。保留的不对称只有两个:纠正信任(防火墙)与 MAX_MEMBERS(成本保险丝)——群可以是平权的,但 API 账单得有人背。落地时发现并修复一个新引入的边界:两个信任成员并发互降会把全群打到零信任、彻底失管——不变式"群内恒有信任成员"必须写成原子条件 UPDATE,先查后改的护栏关不死竞态窗口。

> 落地锚点：`src/homeshield/core/models.py` `Member.trusted`（Role 枚举整体删除,无兼容层）｜`src/homeshield/core/notifier.py`（告警受众 list_adults→list_members）｜`src/homeshield/core/repo.py` `demote_with_guard`（条件 UPDATE 内置不变式,并发窗口关闭）｜`src/homeshield/api/groups.py` `POST /api/members/{id}/trust`（不能改自己+最后信任位护栏）｜`src/homeshield/web/console.html`（按 viewer_trusted/viewer_id 隐藏幽灵按钮）｜《产品定位》决策 #6、v2.3；全量 127 测试通过。

## 供应商 402 撕开的口子：降级路径会丢掉已算出的规则下限（2026-09-26,遗留）

真实链路验收时 DeepSeek 余额不足(402),判定重试耗尽走"拿不准"降级——回执、落库、降级回复、微信送达全部按设计工作,这半边是好消息。但顺着排查发现:`pipeline.run` 的 `except DegradeError` 分支把 `_extract` 已经算出的 `rule_floor` 整体吞掉——规则下限的语义是"无论 LLM 说什么不低于该级",而异常控制流让 LLM 一挂,哪怕消息同时命中"别告诉家人+转账"、规则层可确定性判 dangerous 的消息也降级成 safe 口径,构成对可确定性识别高危的漏报。教训:降级兜底设计必须回答"哪些确定性结论不依赖 LLM";规则下限恰是这种结论,不该躺在被丢弃的 Extraction 里。修复方向已定(降级分支先应用 rule_floor 再决定降级),等指令实施。

> 落地锚点：`src/homeshield/core/pipeline.py` `run()` 的 `except DegradeError` 分支（问题所在,待修）｜`src/homeshield/core/features.py` `rule_floor`（isolation+transfer→dangerous 的确定性下限）｜`src/homeshield/core/models.py` `max_level`（下限合成语义）。

## 机制而非场景：产品提供八件机制，社会学还给用户（2026-09-26）

多群设计讨论收敛出的产品原则：规格里出现任何一个场景假设（"长辈双群""已婚子女守护两家"），就等于替用户做了一次社会学决定，而每次都会做错某一类用户。产品只提供八件机制——建群、邀请、查询、告警广播、信任位、退群/移除、护栏、命名自由——如何组织（家人/邻里/同事）、群叫什么、拉几个人，是用户自己的社会学。机制保证的不变式仅一条：判定回复回到查询者，高危到达查询者所在的每一个群，信任位决定纠正的生效方式。路由设计随之简化：查询永远是私人的（回复不进群），告警广播到查询者所在各群——"默认群+切换命令"被推翻，因为它把上下文管理推给用户且存在选错群的隐私事故；消灭选择优于管理选择。验收线：单群成员严格零感知。

> 落地锚点：`docs/家中盾_产品定位.md` 决策 #7、§1.2（多群模型）、FR-11｜`docs/家中盾_架构技术.md` §2（多租户入群,规格定稿实现待启动）、§4 数据模型（user×membership 拆分）｜六件配套：模板群名字段、我的群/退出命令、控制台群切换器、移除成员、per 群信任位、单群零感知回归测试。
