# 家中盾 会话边界 问题记录

> 版本:v1.0 | 2026-09-27 | 状态:**问题定稿;方案未选型,待立项**
> 读者:研发与测试。关联:《产品定位》v2.7、《架构技术》v2.24(重构四"会话一等公民")、《判定模型_设计教训》v1.2。
> 性质:重大问题记录,非实施规格。本文只钉死问题与候选方向;选型、判据预注册、DDL 留给立项后的规格文档。

## 1. 问题陈述

**系统没有跨消息的会话概念,"一次欺诈检测"的边界被钉死在"一条消息"上。**

真实骗局是多天、多条消息的:骗子先用几天建立信任("在带你赚钱"),再在某个时刻索取("再转 5000 就能提现")。当前系统里,查询者先发一张聊天截图、十分钟后又发一句"他今天又让我转账了",第二条是完全孤立的判定——前文的信任铺垫、上一条的判定级别,对第二条判定不可见。重构四建立的"会话"没有解决这个问题,因为它只在单条消息内部成立。

用户原话(2026-09-27):"现在项目这样的欺诈检测,好像是没有会话的概念……怎么区分用户一次欺诈检测消息的边界。"

## 2. 现状定位(证据)

| # | 事实 | 位置 |
|---|---|---|

当前唯一真实存在的"会话边界"是用户手工完成的:截一张尽量完整的图。边界质量 = 用户截图的耐心。

## 3. 后果

1. **判定上下文残缺**:单条截图装不下多天证据链,judge 每次只见骗局的一个切片。对渐进式骗术(杀猪盘类),单独看任何一条都可能是 safe/suspicious,连起来才是 dangerous——这正是"零漏报"目标的结构性盲区。
2. **升级特征跨消息失效**:现有 `escalation` 是规则层确定性计算,只在消息内生效;跨消息升级(同一 user 的时序消息)天然可以复用同一逻辑,但当前无挂靠点。
3. **额度浪费**:纯确认类消息消耗客服回复额度与判定成本,还可能把"谢谢"判成 safe 并落一条无意义 verdict,污染回流数据。
4. **案件视角缺失**:告警、纠正、周报都以单条 verdict 为粒度,同一骗局的多次查询无法聚合,"这周这个骗局盯上你三次"这类案件级结论无从产生。

## 4. 问题的两半

"边界"实际是两个问题,立项时必须分开回答:

- **归属(上半)**:哪些消息属于同一次案件/会话?——本记录 §5 的主题。
- **分诊(下半)**:一条消息是否构成一次检测请求?闲聊、确认、对上一条回复的感谢,不该触发判定。E4 的现状是"每条都判"。

## 5. 候选方案(归属机制,未选型)

| 方案 | 机制 | 优点 | 缺点/风险 |
|---|---|---|---|
| A 时间窗 | 同一 `user_id`,消息间隔 ≤ N 分钟(如 30min–2h)归同一会话,超时开新会话 | 确定性、零 LLM 成本、可单测;聊天产品标准做法 | 阈值是拍的;分不开"同一时段两个不同骗子";跨天长线骗局被切断 |
| B 语义判定 | 新消息进来时 LLM 判断"是上一件事的延续还是新话题" | 归属准确率上限最高 | 非确定性(与可复现/可证伪文化冲突)、逐条 API 成本、误判无兜底 |
| C 显式+信号修正 | 回复话术引导"解决了回复'新的'";自动修正:新消息含强特征(转账/账号/紧急)且上一判定非 safe 时自动挂接 | 显式重置给用户最终控制权;信号修正零成本纠偏 | 老人产品引导成本高,显式只适合兜底;信号规则需防误挂 |

初步倾向(讨论稿,未决策):**A 为主、C 的信号修正为辅、C 的显式重置为兜底**;B 作为实验开关进入证伪流程,不进默认路径。

## 6. 立项时必须回答的设计点

1. **判定粒度保持逐条**:每条消息仍独立出 verdict(幂等、告警、延迟、评测口径都不动),会话只影响 `JudgeInput`——同会话前几轮(带时间戳与历史判定级别)作为前情注入,设上限防上下文爆炸。
2. **会话挂在查询者而非群**:骗局发生在查询者本人与骗子之间,session key 应为 `user_id`(openid 级);一人多群后尤其不能挂群(`query_group` 是扇出关系,不是归属关系)。
3. **`escalation` 跨消息扩展**:升级特征从"消息内轮次间"推广到"会话内消息间",仍是规则层确定性计算,judge 可引用。
4. **分诊与归属的先后**:先分诊(不判定的消息是否入会话留痕?)再归属,还是归属后再分诊?分诊错误(把关键消息当闲聊)比漏判一次判定更伤,判据需覆盖。
5. **存储形态**:`query` 加可空 `session_id`(回填)或独立 session 表(`user_id, opened_at, last_at`);dev 库重建惯例下无迁移负担。
6. **局限明示**:时间窗分不开同时段双骗子、跨天长线被切断,是所有启发式的共同盲区,设计文档需如实记录,留纠正回流兜底。

## 7. 立项建议

- 体量与先例适合按重构序列推进(多群模型 → 会话模型),走既有纪律:**判据预注册、先证伪再定默认**。
- 可复用的评测基础:重构四的 52 条会话体样本与 `export-conversations` 通道;缺口是**跨消息样本**(同一会话拆成多条消息按时序投喂),需新建导出形态与断点续跑支持。
- 触发时机的两条路线,立项时二选一:(a) 立即立项——它是判定正确性问题,不是可选功能;(b) 观察真实回流——出现"查询者对同一骗局多次投喂"的行为数据后再做,与多群模型的"数据回答需求强度"先例一致。
- 关联遗留:过程总结 §"供应商 402"提到的降级丢 `rule_floor` 问题未修,会话改造会动 `Pipeline.run` 的降级分支,建议同批处理。
