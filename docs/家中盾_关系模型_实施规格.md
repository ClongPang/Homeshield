# 家中盾 关系模型 实施规格

> 版本:v1.3 | 2026-09-28 | 状态:**实现及本地验收完成(2026-09-28);微信实号模板/链接验证部署前完成**
> 读者:研发与测试。设计依据:《产品定位》v2.11/决策 #8、#9、#10(联防关系、多数票与查询级同步);协同层设计取代《家中盾_多群模型_实施规格》,后者保留为历史依据与验收记录。
> 判定契约:features/judge/annotate/knowledge/reply 三段式与会话模型(incident/triage/supply)的判定路径均不动;仅群命令清单换成关系命令,删除零关系拦截。

## 1. 目标与不变式

**目标**:用"双方同意的单向联防关系"取代 `protection_group × member` 容器;用联防者多数票确认纠正;消除群生命周期护栏与双模板;放行裸查询;周报退役。

四条不变式,所有实现决策用它裁决:

| # | 不变式 | 含义与可验证表述 |
|---|---|---|
| I1 | 判定私人且无门槛 | 回执、判定回复、降级提示只回到查询者;零活跃关系的用户文本一律完整判定,不存在"未入群拦截";URL/图片照常进判定 |
| I2 | 提醒沿关系 | 查询受理时固定当时活跃的"被联防"关系快照(可为空);判定完成时(不论判定等级,决策 #10)仅对快照中仍活跃的关系各落一条 alert,每关系至多一条;解除即失权:新提醒不再同步,历史提醒不可再看 |
| I3 | 方向即角色,多数票裁决 | 对某条判定,仅该查询者的合格联防者是信任投票者;查询者的反馈不计票。联防者一人一票,同一标签票数严格超过固定合格人数的一半才成为已核实纠正;零合格联防者或无多数时保留未核实反馈 |
| I4 | 无容器推导一切 | 授权、扇出、投票资格、静音全部从活跃关系推导;不引入群、租户、工作区或任何容器级状态;解除不留下需要护栏的孤儿(无"最后信任成员"类问题) |

**反屎山纪律**:不写旧库迁移层(dev 库重建);不建通用社交图谱框架(只做有向二元关系,无好友申请/留言/动态);不做旧群命令行为兼容(仅一次性迁移提示);不做案件/周报聚合消费端;每个新配置项必须能一句话说清"调它会改变什么行为"。

## 2. 范围

### 2.1 做(P1→P3)
1. schema 重建:`guard_relation`/`invite_code` 取代 `protection_group`/`member`/`bind_code`;`query_relation` 取代 `query_group`;`alert` 与 `correction_case`/`correction_vote` 按关系建模;周报统计查询/接口删除;
2. 命令重写:`邀请 [称呼]` / `绑定 <码>` / `我的联防` / `解除 <称呼>`;旧群命令一次性迁移提示;分诊命令清单同步(删除未绑定引导分支);首次微信消息建立个人身份;
3. 裸查询放行:`/api/query` 与微信文本链路删除零关系 400/引导;
4. 告警扇出:受理快照、判定时活跃校验、单套模板(thing2=被联防者称呼)、按关系静音;
5. 纠正投票:方向语义(I3)、固定投票人快照、绝对多数与无共识终态、「待我投票」队列;
6. 控制台:关系页(邀请/撤销未用邀请码/称呼/静音/解除)、「我收到的提醒」「我的查询」两视图、邀请落地页;SSE 授权改关系。

### 2.2 不做(明确出范围)
| 不做 | 原因 |
|---|---|
| 互保一键邀请、批量邀请、"求护"方向邀请 | 便捷项,真实使用数据裁决后再立项;交换邀请已可达成双向 |
| 关系解除通知对方 | 沿用"移除不通知"现状;观察项 #2 |
| 通用好友/社交图谱能力 | 只服务告警扇出与投票,最小原语 |
| 案件/周报类聚合消费端 | 周报退役;分区数据仍落库,消费端另行立项 |
| 旧群数据迁移兼容层 | dev 库重建;生产部署前仅以新 schema 建库 |
| 会话模型(incident/supply/triage 判定路径)改动 | 正交;仅替换 triage 命令清单中的群命令 |

## 3. 数据模型(DDL,一次性重建 dev 库)

`user` 表不变(openid/token 语义沿现状)。`query`/`verdict`/`incident` 表沿现状。

```sql
CREATE TABLE guard_relation(        -- 一条单向联防关系:protector 联防 protected
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    protector_user_id INTEGER NOT NULL REFERENCES user(id),
    protected_user_id INTEGER NOT NULL REFERENCES user(id),
    name TEXT NOT NULL,              -- 联防者给被联防者的称呼(模板 thing2/列表/详情)
    inverse_name TEXT NULL,          -- 被联防者给联防者的称呼(NULL 显示"联防者")
    mute INTEGER NOT NULL DEFAULT 0, -- 联防者侧静音(仅静模板推送)
    created_at INTEGER NOT NULL,
    ended_at INTEGER NULL,           -- NULL=活跃
    end_reason TEXT NULL CHECK(end_reason IN ('by_protector','by_protected')),
    CHECK(protector_user_id <> protected_user_id),
    CHECK((ended_at IS NULL) = (end_reason IS NULL))
);
CREATE UNIQUE INDEX uq_active_relation
    ON guard_relation(protector_user_id, protected_user_id) WHERE ended_at IS NULL;
CREATE INDEX ix_relation_protected_active ON guard_relation(protected_user_id, ended_at);
CREATE INDEX ix_relation_protector_active ON guard_relation(protector_user_id, ended_at);

CREATE TABLE invite_code(           -- 邀请者=未来联防者,绑定者=未来被联防者
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL UNIQUE,
    creator_user_id INTEGER NOT NULL REFERENCES user(id),
    name TEXT NOT NULL,              -- 预填被联防者称呼,绑定时落库到 guard_relation.name
    created_at INTEGER NOT NULL,
    expires_at INTEGER NOT NULL,
    used_at INTEGER NULL,
    used_by_user_id INTEGER NULL REFERENCES user(id),
    revoked_at INTEGER NULL,        -- 邀请者主动撤销;与 used_at 互斥
    CHECK(NOT (used_at IS NOT NULL AND revoked_at IS NOT NULL)),
    CHECK((used_at IS NULL) = (used_by_user_id IS NULL))
);

CREATE TABLE query_relation(        -- 受理快照:查询者当时的活跃"被联防"关系
    query_id INTEGER NOT NULL REFERENCES query(id),
    relation_id INTEGER NOT NULL REFERENCES guard_relation(id),
    PRIMARY KEY(query_id, relation_id)
);

CREATE TABLE alert(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL REFERENCES verdict(id),
    relation_id INTEGER NOT NULL REFERENCES guard_relation(id),
    name_at_alert TEXT NOT NULL,     -- 判定时称呼;后续改称呼不改历史文案
    delivered_at INTEGER NOT NULL,   -- 告警生成时间,不表示微信模板送达成功
    read_at INTEGER NULL,
    UNIQUE(verdict_id, relation_id)
);

CREATE TABLE correction_case(       -- 一条判定最多一场纠正投票
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL UNIQUE REFERENCES verdict(id),
    queryer_label TEXT NULL CHECK(queryer_label IN ('real','false_positive')),
    queryer_note TEXT NOT NULL DEFAULT '',
    queryer_feedback_at INTEGER NULL,
    status TEXT NOT NULL CHECK(status IN ('pending','confirmed','no_consensus')),
    resolved_label TEXT NULL CHECK(resolved_label IN ('real','false_positive')),
    opened_at INTEGER NOT NULL,
    closes_at INTEGER NOT NULL,
    resolved_at INTEGER NULL,
    CHECK(closes_at > opened_at),
    CHECK((queryer_label IS NULL) = (queryer_feedback_at IS NULL)),
    CHECK((status = 'confirmed') = (resolved_label IS NOT NULL)),
    CHECK((status = 'pending') = (resolved_at IS NULL))
);
CREATE TABLE correction_vote(       -- 创建 case 时写入全部合格关系,空 label 表示未投票
    case_id INTEGER NOT NULL REFERENCES correction_case(id),
    relation_id INTEGER NOT NULL REFERENCES guard_relation(id),
    label TEXT NULL CHECK(label IN ('real','false_positive')),
    voted_at INTEGER NULL,
    PRIMARY KEY(case_id, relation_id),
    CHECK((label IS NULL) = (voted_at IS NULL))
);
CREATE INDEX ix_correction_vote_relation ON correction_vote(relation_id, case_id);
```

**约束与口径**
- 活跃关系 = `ended_at IS NULL`。解除后旧行保留,`query_relation/alert/correction_vote` 等外键引用不删;同方向重建创建**新**关系行,不复活旧行;
- `(protector, protected)` 活跃唯一 → 同一查询者的各联防者天然不重复,`alert` 按 `(verdict_id, relation_id)` 唯一,不再需要跨容器按用户去重;同一接收者的多条关系(护着多个人)分属不同 verdict,互不影响;
- 受理时在同一写事务内插入 `query` 与全部 `query_relation`(取 `protected_user_id = 查询者` 的活跃关系,可为空 = 裸查询);判定时仅对快照中**仍活跃**的关系落 alert。受理后判定前解除 → 该关系不收本条;判定前新建的关系 → 不收旧查询;查询者判定前解除自己全部关系 → 快照空转,照常判定、无告警、回复不出现"已通知"表述;
- 模板发送前复核关系仍活跃且 `mute=0`;`mute=1` 只关该关系的模板,alert 历史与 SSE 保留;解除后等待中的模板不再发送;
- `name_at_alert` 记录判定时称呼;后续改称呼不改历史告警文案;
- **纠正投票**(I3 展开):
  - 信任角色只相对于**该条判定的查询者**成立。用户联防别人,不会因此对自己的查询拥有信任票;查询者本人可提交一条普通反馈,但不计票;
  - 第一条反馈开启 `correction_case`。`dangerous` 可由查询者提交或由收到该条 alert 的联防者直接投票开启;`safe/suspicious` 只由查询者提交后开启。不可对无 verdict 的降级结果投票;
  - 开启时在同一事务中冻结合格投票关系:`dangerous` = 该 verdict 已落 alert 且此刻仍活跃的关系;`safe/suspicious` = `query_relation` 中此刻仍活跃的关系。新关系、未收到该条告警的关系、已结束关系都不能加入旧案;静音关系仍合格;
  - 每条合格关系一票,由其 `protector_user_id` 投 `real` 或 `false_positive`,不可改票;投票时再次确认关系仍活跃。查询者普通反馈仅存 `queryer_label/note`,不增加票数。投票快照的总人数 `N = COUNT(correction_vote)` 固定,门槛 `floor(N/2)+1`;例如 N=1 需 1 票,N=2 需 2 票,N=3 需 2 票。任一标签达门槛即 `confirmed`,记录 `resolved_label`;另一标签不可能随后翻案。创建 case、写入投票人快照、首次投票和每次计票/收口均在同一写锁事务内完成;
  - 未达门槛保持 `pending`,即使双方票数相等也不自动取舍;`now >= closes_at` 时拒绝新票并转 `no_consensus`,不作为已核实样本。N=0 时立即 `no_consensus`:查询者反馈仍留存,不得自证 `confirmed`。期限到达后的首次读/写必须原子收口,不依赖后台定时任务。投票窗口 `closes_at = opened_at + CORRECTION_WINDOW_DAYS`(默认 7;调它改变纠正投票的收口期限,测试经 Settings 覆盖);
  - 关系解除后不再允许该关系投新票或查看原内容;已投票作为审计保留并计入原快照,N 不缩减,以免通过解除改变多数门槛。已确认结果不因后来解除而重算;若剩余票不足,到期为 `no_consensus`;
  - 可信回流只读取 `confirmed` 的 `resolved_label`;原 `verdict`、回复和已发告警不可被投票追溯改写。查询者可在 case 已开启后补交一次普通反馈,不重开已收口的投票;
  - `safe/suspicious` 的原查询内容仅在查询者主动反馈后展示给合格联防者投票;关系绑定文案必须明确告知该范围。已解除者与新联防者不能通过待投票队列读取旧查询;
- **邀请码**:有效条件为未使用、未过期、未撤销;邀请者可撤销未用码。联防者主动解除关系时,同步撤销自己创建的全部未用码,避免其他旧码重新建立已拒绝的关系;被联防者解除不代替邀请者撤销其面向他人的码。发码/认领/撤销在写锁事务内原子完成;
- **解除(唯一终止路径)**:任一端单方立即生效;`end_reason` 记录发起方(`by_protector`/`by_protected`);不通知对方;无护栏——关系解除不产生孤儿容器;共享连接上的仓储访问共用进程内 `threading.RLock`(沿会话模型纪律),落 alert 前复核活跃,并发解除与判定不留悬空推送;
- **护栏**:`MAX_RELATIONS`(每用户活跃关系总数,两个方向合并计,默认 10,替代 `MAX_GROUPS`;`MAX_MEMBERS` 退役——关系无成员位概念);发码时校验创建者额度,绑定时复核双方额度;服务级不设上限。

## 4. 微信命令与消息

### 4.1 命令
每条有效微信消息在分诊/命令解析前按 `openid` 原子 find-or-create user;关注事件仍只发欢迎语。首次处理完成后单独发送个人链接(配置了 `PUBLIC_BASE_URL` 时),不混入三段式判定正文:生产按"回 success + 客服接口异步"投递;被动回复-only 环境(测试号/演示)一条消息只有一条被动回复,首条是判定时不塞入链接、亦不事后补发,链接统一经「我的联防」随时取得。已存在用户同样可通过「我的联防」重新取得。首次消息是邀请、绑定、文字、URL 或图片时均适用。

| 命令 | 行为 | 护栏/文案 |
|---|---|---|
| `邀请 [称呼]` | 生成邀请码与落地链接,预填被联防者称呼(缺省「家人」);回复码、链接与一句说明("TA 绑定后,你将收到 TA 的查询提醒;TA 主动纠正低风险判定时,原查询也会供你投票") | 受 `MAX_RELATIONS` 护栏,达上限拒绝并提示;未用码在控制台可撤销 |
| `绑定 <码>` | 校验码有效(未用、未过期、未撤销),建立关系(protector=码创建者,protected=绑定者);回复知情文案:"TA 会收到你的查询提醒;你主动纠正其他判定时,原查询内容也会给 TA 投票查看;回复「我的联防」查看,「解除」可停止" | 自己绑自己的码拒绝;过期/已用/已撤销码提示;同方向已存在活跃关系提示"已建立这条联防,无需重复绑定";任一方达上限拒绝 |
| `我的联防` | 两段列表:`我护着:#12 妈妈 #13 爸爸(已静音)` / `护着我:#21 儿子`;零关系 → "还没有联防。回复「邀请 称呼」护住家人;也可以直接转发可疑消息给我看";附本人控制台链接 | "我护着"显示 `name`,"护着我"显示本人起的 `inverse_name`,为空显示「联防者 #关系ID」;关系 ID 供同名时精确解除 |
| `解除 <称呼/#关系ID>` | 在本人参与的关系中按本人侧显示名精确匹配,或按 `#关系ID` 终止;按方向措辞回复("已解除:TA 不再收到你的查询提醒"/"已解除:你不再收到 TA 的查询提醒") | 同名多匹配 → 回列表并提示使用关系 ID;控制台可解除任意一条;立即生效,不通知对方;联防者解除时撤销其全部未用邀请码 |
| 旧群命令(开通/我的群/退出/解散) | 一次性迁移提示:"命令已更新:回复「邀请 称呼」发起联防,「我的联防」查看,「解除 称呼」停止" | 不做行为兼容 |
| 其余文本(任何用户) | 一律完整判定(删除零关系拦截与 `BIND_GUIDE_OUTSIDE_GROUP` 分支) | 首次消息可为 URL/图片;triage 命令清单同步更新 |

### 4.2 查询者消息(不变式 I1/I2)
- ACK、三段式判定回复、降级提示均不变,与是否零关系无关;
- 判定完成且判定时仍有活跃快照关系(**不论判定等级**——扇出由查询事件触发,查询本身即"起了疑心"的信号,判定漏报不能静默,决策 #10):在原回复之后补一条**仅查询者可见**的说明,按被联防者自己设置的 `inverse_name` 列出接收者,例如"查询提醒已加入儿子、女儿的提醒列表";未设称呼则显示「联防者 #关系ID」。这只断言 alert 已生成,不声称微信模板送达;静音者仍有提醒列表。快照为空或判定前全部解除 → 不得出现已通知他人的表述;
- WELCOME 更新为三选一:"· 家人给你发了邀请码?回复:绑定 邀请码 · 想守护家人?回复:邀请 称呼 · 也可以直接转发可疑消息给我看";知情句改为"查证结果只回复你本人;你的每次查证都会提醒联防你的人;你主动纠正其他判定时,原查询会给他们投票查看"(一句话说清机制,不做分级披露与防御性措辞);免责口径(96110 露出等)沿 v2.8 不变。零关系用户可回复「我的联防」取得个人控制台链接;网页仍以该链接的个人 token 鉴权,不开放匿名网页查询。

### 4.3 模板消息
- **单套模板**:统一使用带 `thing2` 的模板(现 `WECHAT_MULTI_TEMPLATE_ID` 字段集:`thing1` 摘要 ≤20 字、`phrase1` 高危预警、`thing2` 被联防者称呼);`WECHAT_TEMPLATE_ID`(无 thing2 的单群模板)退役;`thing2` 写 `name_at_alert`,超长按模板字段上限截断;
- 每条 alert 一条模板,发送前复核关系活跃且 `mute=0`;不存在"同一接收者多条关系合并一条"的场景(同一 verdict 对每条关系至多一条);
- 落地页 `/alert/{id}` 结构不变;联防者解除后打开 → 410 与通俗说明"这条提醒的联防关系已解除,无法查看";无关者仍普通 404;
- 两项部署前验证沿多群模型遗留:真实测试号/服务号验证字段配置、称呼截断与链接落地。

## 5. API 契约

### 5.1 上下文规则
- token 定位 **user**;所有接口不再有 `group_id`;关系数据接口按活跃关系授权;微信首条消息创建 user 并发个人链接,既有用户可用「我的联防」重新取得链接;网页只接受个人 token,不接受匿名请求;
- `GET /api/relations`:零关系返回空列表,控制台显示邀请/绑定指引并说明"仍可直接查询";
- 告警:`GET /api/alerts` = 本人作为联防者收到的告警流(全部被联防者合并,条目带 `name_at_alert`,支持 `?relation_id=` 过滤);详情授权 = 本人是该 alert 关系的联防者且关系仍活跃,解除后 410 与原因码 `relation_ended`,无关者 404;
- 「我的查询」:`GET /api/my-queries` = 本人判定历史(级别、纠正状态、时间),`GET /api/my-queries/{verdict_id}` = 本人详情与普通反馈入口;授权均为 `query.user_id` 本人;裸查询同样进入该视图;
- 「待我投票」:`GET /api/corrections` = 本人作为活跃合格联防者可投票的 `pending` case 列表(含 `my_vote`/门槛/截止时间);未投票者显示两种标签按钮,已投票者只看本人票与状态;告警详情同样显示本人的投票状态与按钮。`POST /api/corrections` 根据该 verdict 的查询者/联防者身份原子提交普通反馈或信任票,不带关系上下文;
- SSE:对同一 `verdict_id × user_id` 至多一个事件,payload 带 `name_at_alert`;送出前复核关系仍活跃;解除后不再送;
- 解除后:旧 token 仍定位 user,原关系数据失权;「我的查询」不受影响(个人数据)。

## 9. 风险与观察项
| # | 风险/观察项 | 处置 |
|---|---|---|
| 1 | 邀请方向对"长辈自助"不对路:长辈发邀请会成为晚辈的联防者 | 第一用户是年轻人(决策 #2),主流程不受影响;观察真实回流,必要时立"求护邀请"便捷项 |
| 2 | 解除不通知对方 | 沿用现状;对方经「我的联防」/控制台可见;观察项 |
| 3 | case 开启后联防者全部解除,固定分母使多数无法达到 | 到期 `no_consensus`,不进可信样本;不允许自证或缩小分母 |
| 4 | 被联防者不知道自己被称呼为什么 | 控制台关系页可见 `name`;观察隐私反馈 |
| 5 | 绑定成功不主动通知联防者 | 沿现状(绑定回复只回绑定者);联防者经列表/控制台可见;观察项 |
| 6 | 裸查询放行后的判定成本 | 判定本就服务个人;通知量只随关系数增长,与用户量解耦 |
| 7 | 未用邀请码被转发或在解除后继续使用 | 发码者可在控制台撤销;联防者主动解除时其创建的**全部**未用码同步失效——码无收件人字段,无法只撤发给被解除者的码,无关未用码陪葬是接受的代价(重发成本低);码认领原子化 |
| 8 | safe/suspicious 纠正会使原查询被联防者看到 | 邀请页、绑定回执与纠正按钮旁明确告知;仅查询者主动反馈才开放该条内容 |
