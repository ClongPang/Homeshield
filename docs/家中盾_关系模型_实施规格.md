# 家中盾 关系模型 实施规格

> 版本:v1.0 | 2026-09-27 | 状态:**规格定稿,实施未启动**;状态同步至《架构技术》(实施收口时)
> 读者:研发与测试。设计依据:《产品定位》v2.9/决策 #8(联防关系取代防护群);协同层设计取代《家中盾_多群模型_实施规格》,后者保留为历史依据与验收记录。
> 判定契约:features/judge/annotate/knowledge/reply 三段式与会话模型(incident/triage/supply)的判定路径均不动;仅群命令清单换成关系命令,删除零关系拦截。

## 1. 目标与不变式

**目标**:用"双方同意的单向联防关系"取代 `protection_group × member` 容器;消除群生命周期护栏与双模板;放行裸查询;周报退役。

四条不变式,所有实现决策用它裁决:

| # | 不变式 | 含义与可验证表述 |
|---|---|---|
| I1 | 判定私人且无门槛 | 回执、判定回复、降级提示只回到查询者;零活跃关系的用户文本一律完整判定,不存在"未入群拦截";URL/图片照常进判定 |
| I2 | 告警沿关系 | 查询受理时固定当时活跃的"被联防"关系快照(可为空);dangerous 时仅对快照中仍活跃的关系各落一条 alert,每关系至多一条;解除即失权:新告警不再同步,历史提醒不可再看 |
| I3 | 方向即角色 | 联防者=信任角色:自己的纠正反馈即时生效,可裁决被联防者的 pending 反馈;被联防者=普通角色:反馈进 pending;查询者无任何活跃联防者时,反馈自证生效(提交即 confirmed) |
| I4 | 无容器推导一切 | 授权、扇出、裁决、静音全部从活跃关系推导;不引入群、租户、工作区或任何容器级状态;解除不留下需要护栏的孤儿(无"最后信任成员"类问题) |

**反屎山纪律**:不写旧库迁移层(dev 库重建);不建通用社交图谱框架(只做有向二元关系,无好友申请/留言/动态);不做旧群命令行为兼容(仅一次性迁移提示);不做案件/周报聚合消费端;每个新配置项必须能一句话说清"调它会改变什么行为"。

## 2. 范围

### 2.1 做(P1→P3)
1. schema 重建:`guard_relation`/`invite_code` 取代 `protection_group`/`member`/`bind_code`;`query_relation` 取代 `query_group`;`alert`/`correction` 按关系改造;周报相关表/接口删除;
2. 命令重写:`邀请 [称呼]` / `绑定 <码>` / `我的联防` / `解除 <称呼>`;旧群命令一次性迁移提示;分诊命令清单同步(删除未绑定引导分支);
3. 裸查询放行:`/api/query` 与微信文本链路删除零关系 400/引导;
4. 告警扇出:受理快照、判定时活跃校验、单套模板(thing2=被联防者称呼)、按关系静音;
5. 纠正裁决:方向语义(I3)、「待我裁决」队列、自证生效;
6. 控制台:关系页(邀请/称呼/静音/解除)、「我收到的提醒」「我的查询」两视图、邀请落地页;SSE 授权改关系。

### 2.2 不做(明确出范围)
| 不做 | 原因 |
|---|---|
| 互保一键邀请、批量邀请、"求护"方向邀请 | 便捷项,真实使用数据裁决后再立项;交换邀请已可达成双向 |

| 会话模型(incident/supply/triage 判定路径)改动 | 正交;仅替换 triage 命令清单中的群命令 |

## 3. 数据模型(DDL,一次性重建 dev 库)

`user` 表不变(openid/token 语义沿现状)。`query`/`verdict`/`incident` 表沿现状。

```sql
CREATE TABLE guard_relation(        -- 一条单向联防关系:protector 联防 protected
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    protector_user_id INTEGER NOT NULL REFERENCES user(id),
    protected_user_id INTEGER NOT NULL REFERENCES user(id),
    name TEXT NOT NULL,              -- 联防者给被联防者的称呼(模板 thing2/列表/详情)
    inverse_name TEXT NULL,          -- 被联防者给联防者的称呼(NULL 显示"联防者")
    mute INTEGER NOT NULL DEFAULT 0, -- 联防者侧静音(仅静模板推送)
    created_at INTEGER NOT NULL,
    ended_at INTEGER NULL,           -- NULL=活跃
    end_reason TEXT NULL CHECK(end_reason IN ('by_protector','by_protected')),
    CHECK(protector_user_id <> protected_user_id),
    CHECK((ended_at IS NULL) = (end_reason IS NULL))
);
CREATE UNIQUE INDEX uq_active_relation
    ON guard_relation(protector_user_id, protected_user_id) WHERE ended_at IS NULL;

CREATE TABLE invite_code(           -- 邀请者=未来联防者,绑定者=未来被联防者
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL UNIQUE,
    creator_user_id INTEGER NOT NULL REFERENCES user(id),
    name TEXT NOT NULL,              -- 预填被联防者称呼,绑定时落库到 guard_relation.name
    created_at INTEGER NOT NULL,
    expires_at INTEGER NOT NULL,
    used_at INTEGER NULL,
    used_by_user_id INTEGER NULL REFERENCES user(id)
);

CREATE TABLE query_relation(        -- 受理快照:查询者当时的活跃"被联防"关系
    query_id INTEGER NOT NULL REFERENCES query(id),
    relation_id INTEGER NOT NULL REFERENCES guard_relation(id),
    PRIMARY KEY(query_id, relation_id)
);

CREATE TABLE alert(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL REFERENCES verdict(id),
    relation_id INTEGER NOT NULL REFERENCES guard_relation(id),
    name_at_alert TEXT NOT NULL,     -- 判定时称呼;后续改称呼不改历史文案
    delivered_at INTEGER NOT NULL,   -- 告警生成时间,不表示微信模板送达成功
    read_at INTEGER NULL,
    UNIQUE(verdict_id, relation_id)
);

CREATE TABLE correction(            -- 结构按多群模型 v1.6,裁决外键改为关系
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL REFERENCES verdict(id),
    by_user_id INTEGER NOT NULL REFERENCES user(id),
    label TEXT NOT NULL CHECK(label IN ('real','false_positive')),
    note TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL CHECK(status IN ('pending','confirmed','rejected')),
    decided_by_relation_id INTEGER NULL REFERENCES guard_relation(id),
    created_at INTEGER NOT NULL,
    decided_at INTEGER NULL,
    UNIQUE(verdict_id, by_user_id)
);
```

**约束与口径**
- 活跃关系 = `ended_at IS NULL`。解除后旧行保留,`query_relation/alert/decided_by_relation_id/invite_code.used_by_user_id` 等外键引用不删;同方向重建创建**新**关系行,不复活旧行;
- `(protector, protected)` 活跃唯一 → 同一查询者的各联防者天然不重复,`alert` 按 `(verdict_id, relation_id)` 唯一,不再需要跨容器按用户去重;同一接收者的多条关系(护着多个人)分属不同 verdict,互不影响;
- 受理时在同一写事务内插入 `query` 与全部 `query_relation`(取 `protected_user_id = 查询者` 的活跃关系,可为空 = 裸查询);判定时仅对快照中**仍活跃**的关系落 alert。受理后判定前解除 → 该关系不收本条;判定前新建的关系 → 不收旧查询;查询者判定前解除自己全部关系 → 快照空转,照常判定、无告警、回复不出现"已通知"表述;
- 模板发送前复核关系仍活跃且 `mute=0`;`mute=1` 只关该关系的模板,alert 历史与 SSE 保留;离群等待中的模板不再发送;
- `name_at_alert` 记录判定时称呼;后续改称呼不改历史告警文案;
- **纠正权利**(I3 展开):
  - `safe/suspicious`:仅查询者本人可反馈;提交时存在活跃联防者 → `pending`,否则直接 `confirmed`(自证);
  - `dangerous`:查询者本人 + 快照中判定时活跃且**当前仍活跃**关系的联防者可反馈;联防者提交 → 即 `confirmed`,`decided_by_relation_id` 记其关系,`decided_at=created_at`;查询者提交 → `pending`,由其任一活跃联防者裁决一次;提交时联防者已全部解除 → 按无联防者自证;
  - 裁决权校验:裁决时裁决者必须是该 `verdict` 所属查询者的活跃联防者;`decided_by_relation_id` 保留裁决时的关系;
  - `pending` 反馈把原查询内容展示给裁决者(被查询者的联防者本就有权见其高危摘要),按钮旁说明这一点,不加确认步骤;
  - `pending` 提交后裁决者全部解除 → 状态不变、不进统计(观察项 #3);`rejected/confirmed` 为终态;
- **解除(唯一终止路径)**:任一端单方立即生效;`end_reason` 记录发起方(`by_protector`/`by_protected`);不通知对方;不牵连邀请码(码建立的是新关系);无护栏——关系解除不产生孤儿容器;共享连接上的仓储访问共用进程内 `threading.RLock`(沿会话模型纪律),落 alert 前复核活跃,并发解除与判定不留悬空推送;
- **护栏**:`MAX_RELATIONS`(每用户活跃关系总数,两个方向合并计,默认 10,替代 `MAX_GROUPS`;`MAX_MEMBERS` 退役——关系无成员位概念);发码时校验创建者额度,绑定时复核双方额度;服务级不设上限。

## 4. 微信命令与消息

### 4.1 命令
| 命令 | 行为 | 护栏/文案 |
|---|---|---|
| `邀请 [称呼]` | 生成邀请码与落地链接,预填被联防者称呼(缺省「家人」);回复码、链接与一句说明("TA 绑定后,你将收到 TA 的高危提醒") | 受 `MAX_RELATIONS` 护栏,达上限拒绝并提示 |
| `绑定 <码>` | 校验码有效(未用、未过期),find-or-create user,建立关系(protector=码创建者,protected=绑定者);回复知情文案:"已建立联防:TA 将收到你的高危提醒;回复「我的联防」查看,「解除」可随时停止" | 自己绑自己的码拒绝;过期/已用码提示;同方向已存在活跃关系提示"已建立这条联防,无需重复绑定";任一方达上限拒绝 |
| `我的联防` | 两段列表:`我护着:1.妈妈 2.爸爸(已静音)` / `护着我:1.儿子`;零关系 → "还没有联防。回复「邀请 称呼」护住家人;也可以直接转发可疑消息给我看" | "护着"段显示 `name`,"护着我"段显示本人起的 `inverse_name`,为空显示「联防者」 |
| `解除 <称呼>` | 在本人参与的关系中按列表显示名精确匹配并终止(联防者侧匹配 `name`,被联防者侧匹配 `inverse_name`,空按「联防者」匹配);按方向措辞回复("已解除:TA 不再收到你的高危提醒"/"已解除:你不再收到 TA 的高危提醒") | 无匹配/多匹配 → 回「我的联防」列表引导;控制台可解除任意一条;立即生效,不通知对方 |
| 旧群命令(开通/我的群/退出/解散) | 一次性迁移提示:"命令已更新:回复「邀请 称呼」发起联防,「我的联防」查看,「解除 称呼」停止" | 不做行为兼容 |
| 其余文本(任何用户) | 一律完整判定(删除零关系拦截与 `BIND_GUIDE_OUTSIDE_GROUP` 分支) | triage 命令清单同步更新;URL/图片仍直接判定 |

### 4.2 查询者消息(不变式 I1/I2)
- ACK、三段式判定回复、降级提示均不变,与是否零关系无关;
- dangerous 且判定时仍有活跃快照关系:在原回复之后补一条**仅查询者可见**的说明,按关系逐一列出("已提醒「妈妈」"或"已提醒妈妈、爸爸");快照为空或判定前全部解除 → 不得出现"已通知"表述;
- WELCOME 更新为三选一:"· 家人给你发了邀请码?回复:绑定 邀请码 · 想守护家人?回复:邀请 称呼 · 也可以直接转发可疑消息给我看";知情句改为"查证结果只回复你本人;判定为高危时,会提醒联防你的人";免责口径(96110 露出等)沿 v2.8 不变。

### 4.3 模板消息
- **单套模板**:统一使用带 `thing2` 的模板(现 `WECHAT_MULTI_TEMPLATE_ID` 字段集:`thing1` 摘要 ≤20 字、`phrase1` 高危预警、`thing2` 被联防者称呼);`WECHAT_TEMPLATE_ID`(无 thing2 的单群模板)退役;`thing2` 写 `name_at_alert`,超长按模板字段上限截断;
- 每条 alert 一条模板,发送前复核关系活跃且 `mute=0`;不存在"同一接收者多条关系合并一条"的场景(同一 verdict 对每条关系至多一条);
- 落地页 `/alert/{id}` 结构不变;联防者解除后打开 → 410 与通俗说明"这条提醒的联防关系已解除,无法查看";无关者仍普通 404;
- 两项部署前验证沿多群模型遗留:真实测试号/服务号验证字段配置、称呼截断与链接落地。

## 5. API 契约

### 5.1 上下文规则
- token 定位 **user**;所有接口不再有 `group_id`;关系数据接口按活跃关系授权;
- `GET /api/relations`:零关系返回空列表,控制台显示开通/邀请指引并说明"仍可直接查询";
- 告警:`GET /api/alerts` = 本人作为联防者收到的告警流(全部被联防者合并,条目带 `name_at_alert`,支持 `?relation_id=` 过滤);详情授权 = 本人是该 alert 关系的联防者且关系仍活跃,解除后 410 与原因码 `relation_ended`,无关者 404;
- 「我的查询」:`GET /api/my-queries` = 本人判定历史(级别、纠正状态、时间),授权 = `query.user_id` 本人;裸查询的判定同样进入该视图——这是查询者查看自己判定的唯一控制台入口;
- 待我裁决:`GET /api/corrections` = 本人作为活跃联防者可裁决的 pending 列表;`POST /api/corrections` 服务端按 §3 权利规则定权,不带关系上下文;
- SSE:对同一 `verdict_id × user_id` 至多一个事件,payload 带 `name_at_alert`;送出前复核关系仍活跃;解除后不再送;
- 解除后:旧 token 仍定位 user,原关系数据失权;「我的查询」不受影响(个人数据)。

### 5.2 接口
| 方法/路径 | 说明 | 变更类型 |
|---|---|---|
| GET `/api/relations` | `{guardings:[{id,name,mute,created_at}],guardians:[{id,name}]}` | **新增** |
| POST `/api/relations/invites` | `{name}` → `{code,join_url}` | **新增** |
| PATCH `/api/relations/{rid}` | 各端改自己侧称呼(联防者改 `name`,被联防者改 `inverse_name`);联防者可改 `mute` | **新增** |
| DELETE `/api/relations/{rid}` | 本人任一端单方解除 | **新增** |
| GET `/api/my-queries` | 本人判定历史与纠正状态 | **新增** |
| GET `/api/alerts` | 本人收到的告警流,`?relation_id=` 过滤 | 改(去 group_id) |

| GET `/api/corrections` | 待我裁决列表 | 改(去 group_id) |

| GET `/api/weekly`、`/api/groups` 系列 | 周报与全部群接口 | **移除** |

## 7. 测试计划(交付测试团队)

### 7.1 回归组(个人闭环,R 系列)
| 用例 | 步骤 | 预期 |
|---|---|---|
| R1 | 零关系用户发文本查询 | ACK/三段式/降级提示正常,与有关系用户一致;dangerous 无 alert、回复无"已通知"表述 |
| R2 | 零关系用户对 safe 判定反馈 | 自证 confirmed;对 dangerous 同理 |
| R3 | 无效 token 401;同 MsgId 重发 409;LLM 故障降级"拿不准"不落 verdict | 沿现状 |
| R4 | 会话模型回归:ack/reset/incident/supply 既有用例 | 全绿,不受关系改造影响 |

### 7.2 关系组(G 系列)
| 用例 | 步骤 | 预期 |
|---|---|---|
| G1 | A 回复「邀请 妈妈」,B 绑定该码 | 关系建立(A→B),name 预填;B 收到知情文案(高危将同步给 A + 解除指引);A 的「我护着」出现"妈妈" |
| G2 | A 邀 B 且 B 邀 A | 两条独立关系;各自「我的联防」两段列表正确;解除一条不影响另一条 |
| G3 | B 查 dangerous,有两名联防者 A1/A2,其中 A2 静音 | A1、A2 各落一条 alert;A1 收模板(thing2=称呼),A2 不推;B 的判定回复后附"已提醒妈妈、爸爸"(按各自称呼) |

## 9. 风险与观察项
| # | 风险/观察项 | 处置 |
