## 1. 系统架构

### 1.1 判定管线
```
                    ┌────────────────────────────────────────┐
 ┌──────────┐ text  │  intake 归一化                          │
 │ 长辈聊天页 │──────▶│  → Message{type, content, member, ts}  │
 │ (web/)    │ url  │└───────────────┬────────────────────────┘
 └──────────┘ img   │                ▼
                    │  features.py  规则抽取 + LLM 补抽
 ┌──────────┐       │  → [Feature{id,type,value,span,source}]        0.5s
 │ 判定引擎   │       │                ▼
 │ core/     │◀─────│  retrieval.py  混合检索知识库 top-2             0.3s
 └──────────┘       │                ▼
                    │  judge.py     分级判定(LLM,约束引用特征ID)
                    │  → {level, cited_ids[], reason}                4.0s
                    │                ▼
                    │  validate     引用校验(失败重试≤2)
                    │                ▼
                    │  reply.py     大白话三段式生成                  2.0s
                    │                ▼
                    │  落库(verdict) → dangerous? → notifier(SSE)   <0.5s
                    └────────────────────────────────────────┘
```

**管线约定**:
- 检索 query 由规则特征构造;LLM 补抽与检索并行、补抽结果只喂 judge;
- judge prompt 声明检索案例仅供类目知识与应对建议、"相似≠诈骗",防检索锚定误报;
- **延迟为设计参考值(非验收标准)**:上图各阶段秒数仅用于模型选型与管线结构决策;端到端目标 10s 量级——"秒级判定"是产品 UX 阈值(长辈的等待上限),不是工程验收门槛;延迟只作为评测指标报告(§6.2),不作为 done-when。超时应对:生成阶段先回"结论行"再补依据(流式)。

### 1.2 双模式
`MockJudge`(纯规则:关键词+特征计数打分,确定性)与 `LLMJudge` 实现同一 `Judge` 接口,`.env` 的 `MODE` 切换。Mock 仅做 CI 回归与离线演示;消融矩阵在 LLM 模式下跑(§6.3)。

## 2. 接入通道
- **微信(长辈主入口)**:演示用公众平台测试号(客服接口/模板消息免认证开放,平台规则核验于 2026-09,备选方案取舍见《产品定位》§4.2)。回调按消息类别派发,家人在 5s 窗口内得到可见回应:开通/绑定命令(`开通`、`绑定 <码>`)同步回执行结果(纯 DB 操作),文字/图片回执"收到,正在帮你看…",语音/视频等暂不支持类型立即回兜底提示(请打字或发截图),关注事件回欢迎语(含开通/绑定指引);正式判定经客服接口异步回复(48h 内 5 条额度)。生产用认证服务号:客服接口异步回复 + 模板消息告警,接入阶梯写进 README(《产品定位》§3 D4)。
- **多群入群(src/homeshield/core/binding,groups)**:身份与成员关系分离——`user`(一个微信号一行:openid/token)×`member`(某人在某群的成员关系:昵称/信任位),同一微信号可加入多个防护群。自助开通:回复`开通 [群名]`→ 建群并使发送者成为群主(trusted,未命名用默认);邀请绑定:信任成员创建成员位并生成 8 位一次性绑定码(默认 7 天有效,重发即作废旧码),家人回复`绑定 <码>`落到成员位(默认不受信任)。群内命令:`我的群`、`退出 <群名>`、创建者`解散 <群名>`;信任成员可在控制台移除成员。退群/移除只终止关系并保留历史,最后一名已绑定成员退出自动解散;创建者仍在群内且为信任成员时可主动解散。未绑定的其他消息只引导不判定(不落库、不耗判定资源);user 存在但**零活跃成员关系**(全部退出/所在群解散)同样只引导,裸「开通」直接建新群;护栏 `MAX_GROUPS`(未解散群数)×`MAX_MEMBERS`(每群活跃成员位数),同群同用户最多一条活跃关系由部分唯一索引保证。**单群成员零感知**:群切换器仅在多群时显示;带群名模板仅用于多群接收者;按群页面始终显示当前群名。生命周期细则见《家中盾_多群模型_实施规格》§5.3。
- **网页聊天页(兜底)**:粘贴文字或上传截图,归一化进同一 intake(§1.1)。
- **告警双通道(多群广播)**:查询受理时固定 `query_group`,dangerous 判定时给其中仍活跃群的已绑定成员各落一条 alert;微信模板和 SSE 均按接收 `user_id × verdict_id` 去重。单群接收者沿用现有模板,多群接收者的模板显示相关未静音群名;每群静音只影响模板,不隐藏历史/SSE。控制台先渲染本人有权查看的历史,SSE 补增量;退群后旧流立即撤权。查询回复/回执/降级提示只回查询者。详细时序与授权见《家中盾_多群模型_实施规格》v1.3。
- **异常与守护**:管线意外故障在 VerificationService 收口为人话兜底回复,家人不会遇到 500 或沉默;进程由 systemd / launchd 单元守护(deploy/),崩溃自动重启。

## 3. 判定与协同规则

### 3.1 告警触发
仅 `level='dangerous'` 向查询时相关、判定时仍活跃的群生成 alert,再给其当前接收者发送 SSE(每人每判定一次,payload 带相关 `group_ids/group_names`);`suspicious` 只进周报(打扰预算)。

### 3.2 隔离话术策略(规则下限)
特征类型 `isolation`(初始词表:"别告诉家人/子女""保密""这是我们俩的事""影响他工作"…)命中即至少 `suspicious`;与 `transfer`(要求转账)类特征共现 → 直接 `dangerous`;规则结果为下限,最终 level = max(规则级, LLM 判定级)。三段式判定结构不变;"已通知家人"只在实际生成高危告警后由协同层输出,`suspicious` 与无可接收群的判定不得虚称已通知。

### 3.3 纠正状态机(信任位 per 群)
每个 `verdict_id × user_id` 最多一条纠正,用户一次点击、不选群。dangerous 的有权反馈群=本人当时收到 alert 的群与当前活跃群的交集;safe/suspicious 仅原查询者可反馈,范围为查询时相关群与当前活跃群的交集。服务端把范围写入 `correction_group`;任一相关群有信任位则直接 confirmed,否则 pending;范围内任一当前信任成员可确认/拒绝一次,所有相关群队列同步消失。`pending` 超时(7 天)自动 rejected;只把 confirmed 算进周报与有效样本。信任位与年龄无关;最后信任成员护栏迁移至群维度。

### 3.4 隐私规则
查询回复只回查询者,不进群;仅高危告警向相关群接收者展示摘要(≤20 字)+ 链接,多群接收者另见相关群名。告警详情仅对判定时实际收到 alert、现在仍在至少一个接收群的本人开放;新成员不能看入群前告警,退出者重入后只恢复自己曾收到的记录。提交 pending 纠正会把该条查询内容展示给相关群信任成员,反馈按钮旁说明;系统无被动采集入口。首次进入展示知情页(承载方式见《产品定位》§1.3)。

## 4. 数据模型(SQLite,字段级)
```sql
user(id PK, openid TEXT UNIQUE NOT NULL, -- 真实用户为微信 openid;demo:/test: 前缀仅演示/测试
     token TEXT UNIQUE NOT NULL,         -- 控制台"链接即凭证"(用户级,不随群)
     created_at)                         -- 多群改造后 user 承载身份,member 承载群内关系
protection_group(id PK, name, created_by_user_id FK NULL, created_at, disbanded_at NULL) -- 群实体;SQLite 中避免使用保留字 group
member(id PK, group_id FK, user_id FK NULL, name,
       trusted INTEGER DEFAULT 0(纠正信任位:1=本群纠正即时生效+可管理本群), mute INTEGER DEFAULT 0,
       created_at, ended_at NULL, end_reason NULL)     -- 终止关系留行供历史外键引用;多群=多行
CREATE UNIQUE INDEX uq_active_member ON member(group_id,user_id)
  WHERE user_id IS NOT NULL AND ended_at IS NULL;      -- 仅活跃关系唯一;重入群新建一行
bind_code(id PK, code TEXT UNIQUE, member_id FK, created_by FK NULL,
          created_at, expires_at, used_at NULL)   -- 一次性入群凭证,领取/过期/重发即失效
query(id PK, user_id FK, content_type TEXT CHECK(content_type IN ('text','url','image')),
      content TEXT, msg_id TEXT NULL, created_at)  -- 查询者身份;image 存 base64 或本地路径
query_group(query_id FK, group_id FK, query_member_id FK, PK(query_id,group_id))
   -- 受理时相关群与查询者当时成员关系的快照;不存在单一记账群
verdict(id PK, query_id FK, level TEXT CHECK(level IN ('safe','suspicious','dangerous')),
        cited_ids TEXT,      -- JSON 数组,如 ["F01","F04"]
        features TEXT,       -- 全量特征快照(JSON),供纠正回流复盘与消融分析
        reason TEXT, reply TEXT, latency_ms INT,
        mode TEXT CHECK(mode IN ('mock','llm')), created_at)
alert(id PK, verdict_id FK, membership_id FK(=member.id), group_name_at_alert TEXT,
      delivered_at INT, read_at INT NULL, UNIQUE(verdict_id,membership_id))
   -- dangerous 按"相关群×判定时活跃已绑定成员关系"落行;delivered_at 不代表微信成功
correction(id PK, verdict_id FK, by_user_id FK, label TEXT CHECK(label IN ('real','false_positive')),
           -- label 语义: 提交时的用户主张,永不改写——real=漏报主张; false_positive=误报主张; 是否已核实只看 status
           note TEXT, status TEXT CHECK(status IN ('pending','confirmed','rejected')),
           decided_by_membership_id FK NULL, created_at, decided_at NULL,
           UNIQUE(verdict_id,by_user_id))
correction_group(correction_id FK, group_id FK, by_membership_id FK,
                 PK(correction_id,group_id))  -- 提交时的有权反馈群快照
```

**关键约束**:`query` 与其全部 `query_group` 在同一写事务受理;`alert` 仅由 dangerous verdict 触发,按查询时相关且判定时活跃的群成员落行。历史告警需同时验证本人当时收到过 alert 与现在仍在该群;退群/移除不删 member,解散群终止全部活跃关系并作废邀请码;已打开的 SSE 送出前复查授权。活跃群只要仍有已绑定成员,至少保留一名活跃且已绑定的信任成员;最后一人退出自动解散。周报按 `query_group`/`alert`/`correction_group` 分群计数,多群数字不可相加视作全局总量。完整 DDL 与状态机见《家中盾_多群模型_实施规格》v1.3 §3/§5。

## 5. API 契约

家人接口以 token(不可枚举)定位**用户**,无/错 token 一律 401,接口不回传 token。查询、告警详情、提交纠正不要求选群;告警列表、待确认队列与周报按 `group_id` 选真实群,多群用户必传,单群用户可省略。群数据只对当前活跃成员开放;告警详情还要求本人当时实际收到告警。成员管理和纠正确认由当前相关群信任成员执行;`GET /api/groups` 列出所在群,不标默认群。

| 方法/路径 | 请求 | 响应 | 说明 |
|---|---|---|---|
| POST `/api/query` | `{token, content, content_type?, msg_id?}` | `{query_id, verdict_id, level, cited_ids, reply, latency_ms}` | 同步返回判定;dangerous 时异步广播 |
| GET `/api/groups?token=` | — | `{groups: [{id, name, trusted, member_count}]}` | 我的群列表(多群成员;单群同样可用) |
| DELETE `/api/groups/{gid}` | `{token}` | `{}` | 仅仍在群内的创建者信任成员可主动解散;历史留库,家人访问即撤销 |
| GET `/api/stream?token=` | — (SSE) | `event: alert, data: {verdict_id, group_ids, group_names, summary}` | 本人每判定一条;每条发送前复查访问权 |
| GET `/api/alerts?token=&group_id=` | — | `{alerts: [{verdict_id, level, summary, delivered_at}]}`(新→旧,按判定去重) | 仅本人当时收到且当前仍有权查看的本群高危告警 |
| GET `/api/alerts/{verdict_id}?token=` | — | `{level, reply, summary, created_at, my_feedback, group_names}` | 本人当时收到且仍在接收群才可看;原接收者失权 410,其余无权者 404 |
| GET `/alert/{verdict_id}?token=` | — | 静态页 | 告警落地页:详情 + 一键反馈(误报 / 真骗局) |
| GET `/api/corrections?token=&group_id=` | — | `{viewer_trusted, pending: [{id, label, note, content, by_name, created_at}]}` | 本群待确认队列;多群必传 `group_id` |
| POST `/api/corrections` | `{token, verdict_id, label, note?}` | `{correction_id, status}` | 服务端算有权反馈群;同一人同一判定只反馈一次,不传群 |
| POST `/api/corrections/{id}/confirm` | `{token, decision?}`(confirm/reject) | `{status}` | 任一相关群当前信任成员裁决一次 |

| POST `/api/groups/{gid}/members` | `{token, name}` | `{member_id, name, trusted, bind_code, bind_expires_at, entry_url?}` | 创建成员位(默认不受信任)并签发绑定码;仅本群信任成员,`MAX_MEMBERS` 封顶 |
| POST `/api/groups/{gid}/members/{id}/trust` | `{token, trusted}` | `{member_id, trusted}` | 本群纠正信任位翻转;仅信任成员,不能改自己,降级走最后信任成员护栏 |
| DELETE `/api/groups/{gid}/members/{id}` | `{token}` | `{}` | 移除成员(终止关系、保留历史 user/openid);仅信任成员,最后信任成员护栏 |
| POST `/api/groups/{gid}/members/{id}/bind-code` | `{token}` | `{bind_code, bind_expires_at}` | 重发绑定码(作废旧码);仅本群信任成员,成员须未绑定 |
| GET `/api/weekly?token=&group_id=` | — | `{group_id, days, queries, dangerous, false_positives, corrections}` | 按真实群周报;多群必传 `group_id`,pending 不计数 |
| GET `/` 、 GET `/console` | — | 静态页 | 长辈聊天视图 / 子女控制台(链接即凭证) |
| POST `/wechat/callback` | 微信消息回调 | 被动回复 success/空串(ACK) | 测试号/服务号消息入口;平台签名鉴权;判定结果经客服接口异步回复 |

## 6. 评测规格

**收敛标准(评测纪律,高于本节其余内容)**:
- 唯一的质量收敛标准是**真实世界使用**:真实查询日志、confirmed 纠正(库内留存)、真机/真通道延迟;
- mock、种子样例、合成数据只有两个合法用途:① CI 管道正确性回归;② 冷启动冒烟。**禁止**作为任何质量指标(Recall/FPR/延迟)的收敛与拟合目标——对着自产数据调词表、提示词、阈值,就是"虚假环境陷阱";
- 调整纪律:词表、提示词、阈值、检索权重的每次变更,必须附真实数据复测证据(库内纠正重放或真机日志),否则不合入;
- 报告纪律:`docs/reports/report.md` 强制标注数据来源构成与模式口径;mock 口径的数字只能表述为"管道验证",不得表述为产品质量;
- 配比纪律:§6.1 的样本构成只约束冷启动集 v1;真实使用启动后,数据分布与扩充由真实回流决定,不再按预设配比制造样本。

### 6.1 数据集(`data/samples/`,JSONL,每行一条)
- **规模与构成**:80-100 条;诈骗 40 / 边缘 30 / 正常 30。
- **字段**:`{id, text, label: scam|edge|benign, scam_type(诈骗类才有,对齐分类学), source: "adapted:<出处>"|"synthetic:llm:<model>", notes}`。
- **分层要求**:scam 中 ≥20 条标注 `source=synthetic:llm:*`(由 LLM 生成+人工改写),用于"AI 生成话术检测退化"子评测(中文首发数据点,对标 Frontiers 2026 的英文结论)。
- **边缘档必须覆盖**:真实兼职群、真快递理赔、家人借钱、正常营销短信。
- **来源可溯**:来源与改编方式逐条记录 provenance,防"人造感"质疑。
- **扩展集(候选,不入 v1 主集)**:`data/samples/fraud_r1_base.jsonl`(32 条,8 类均衡,`source=synthetic:llm:deepseek-r1`,**待人工过筛**,已扫描 6/32 含生成残留)与 `data/samples/fraud_r1_levelup.jsonl`(128 条 = 32 案例 × 增强级 0~3 配对,专供"AI 生成话术检测退化曲线");`uv run homeshield-kbcli export-eval` 一条命令复现(§7.3)。

### 6.2 指标定义(公式进 `src/homeshield/eval/run_eval.py` 与报告)
- 检出率 Recall = TP / (TP+FN);TP = 标注 scam 且判为 dangerous+suspicious(dangerous 单列);
- 误报率 FPR = FP / (FP+TN);FP = 标注 benign/edge 且判为 dangerous;
- 分级混淆矩阵(3×3);延迟 P50/P95;分档报告 scam 子集(人工 vs LLM 生成)。

### 6.3 消融矩阵(全部在两种模式下跑)
| 配置 | 特征抽取 | 知识库检索 | LLM 判定约束 | 说明 |
|---|---|---|---|---|
| A(zero-shot) | — | — | 无约束 | 基线 |
| B(A+RAG) | — | ✓ | 无约束 | 检索增益 |
| C(B+约束) | ✓ | ✓ | 引用校验 | 完整方案 |

### 6.4 阈值扫描
判定置信分 → P/R 曲线;工作点按"误报权重高于漏报"选取(产品依据:误报三次=家人拉黑=产品死亡),依据写入报告。

### 7.2 安装与运行(Python 3.12,uv 管理)
- 安装:首次 `uv python pin 3.12` 固定解释器,然后 `uv add openai fastapi "uvicorn[standard]" pydantic python-dotenv httpx`、`uv add --dev pytest`(依赖进 pyproject.toml,锁定 uv.lock,自动创建虚拟环境);`uv sync` 以 editable 方式安装 homeshield 包(`[project.scripts]` 提供三个入口);
- 配置 `.env`:`MODE=llm|mock`;供应商任意命名,每个供应商三件套 `<NAME>_API_KEY / <NAME>_BASE_URL / <NAME>_MODEL`(OpenAI 兼容端点);任务分工 `CHAT_PROVIDER`(判定/补抽/回复)、`TRANSCRIBE_PROVIDER`(图片转写,留空回落 chat)、`EMBED_PROVIDER`(向量检索,留空则纯关键词);
- 运行:`uv run uvicorn homeshield.server:app --reload`;测试:`uv run pytest tests/`;入口:`homeshield-cli`(运维/演示)、`homeshield-kbcli`(离线素材库)、`homeshield-eval`(评测);
- 注意:脚本与测试统一经 `uv run` 执行,不手工 pip install;Python 3.12 下 `match`、`X | Y` 类型联合等新语法可用。

### 7.3 离线素材库(kbbuild,与运行时隔离)
- **定位**:离线批处理资产,服务链路(server/cli/core)永不读取;只有人工审核后的产出物(词表/案例/评测样本)单向进入版本库。
- **数据**:`data/kb_build.db`(`*.db` 已 gitignore):`fr_case`(Fraud-R1 中文语料 4,280 行 = 1,070 案例 × 增强级 0~3,provenance 与许可注记逐行落库)、`fr_tactic_extract`(战术挖掘,预留)、`marker_candidate`(词表审核队列,状态机仿 correction);源文件在 `data/raw/fraud-r1/`(gitignore)。
- **工具**:`uv run homeshield-kbcli init-db|import|stats|export-eval`(不依赖 .env/LLM,零运行时耦合)。
- **类目映射**:`kbbuild/mapping.py` 将 Fraud-R1 五大类对齐 12 类分类学(834/1,070 可映射);phishing 三个子类(236 条)为分类学缺口,映射外不导出,建议后续新增"钓鱼链接/中奖"类目(规格允许 ≥12 类)。
- **红线**:原始语料许可为 HF gated——仅研究/教育用途、不得向第三方转发、不得商用,严禁随产品分发、严禁进公开仓库;评测集并入主集前必须人工过筛(§6.1 扩展集)。
