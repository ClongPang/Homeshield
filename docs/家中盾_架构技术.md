## 1. 系统架构

### 1.1 判定管线
```
                    ┌────────────────────────────────────────┐
 ┌──────────┐ text  │  intake 归一化                          │
 │ 长辈聊天页 │──────▶│  → Message{type, content, relation_ids, ts}  │
 │ (web/)    │ url  │└───────────────┬────────────────────────┘
 └──────────┘ img   │                ▼
                    │  features.py  规则抽取 + LLM 补抽
 ┌──────────┐       │  → [Feature{id,type,value,span,source}]        0.5s
 │ 判定引擎   │       │                ▼
 │ core/     │◀─────│  retrieval.py  混合检索知识库 top-2             0.3s
 └──────────┘       │                ▼
                    │  judge.py     分级判定(LLM,约束引用特征ID)
                    │  → {level, cited_ids[], reason}                4.0s
                    │                ▼
                    │  validate     引用校验(失败重试≤2)
                    │                ▼
                    │  reply.py     大白话三段式生成                  2.0s
                    │                ▼
                    │  落库(verdict) → 生成提醒 / notifier(SSE)      <0.5s
                    └────────────────────────────────────────┘
```

**管线约定**:
- 检索 query 由规则特征构造;LLM 补抽与检索并行、补抽结果只喂 judge;
- judge prompt 声明检索案例仅供类目知识与应对建议、"相似≠诈骗",防检索锚定误报;
- **延迟为设计参考值(非验收标准)**:上图各阶段秒数仅用于模型选型与管线结构决策;端到端目标 10s 量级——"秒级判定"是产品 UX 阈值(长辈的等待上限),不是工程验收门槛;延迟只作为评测指标报告(§6.2),不作为 done-when。超时应对:生成阶段先回"结论行"再补依据(流式)。

### 1.2 双模式
`MockJudge`(纯规则:关键词+特征计数打分,确定性)与 `LLMJudge` 实现同一 `Judge` 接口,`.env` 的 `MODE` 切换。Mock 仅做 CI 回归与离线演示;消融矩阵在 LLM 模式下跑(§6.3)。

## 2. 接入通道
- **微信**:平台签名校验后，首条有效文字、URL 或图片消息按 openid 原子创建 user，再走完整判定；订阅事件只发欢迎语。文字/图片在回调窗口先回执，结果经客服接口回复。生产配置 `PUBLIC_BASE_URL` 后，在首次处理完成后单独发送个人链接；被动回复-only 环境不额外补发链接。
- **命令**:`邀请 [称呼]` 创建邀请码；`绑定 <码>` 建立邀请者→绑定者关系；`我的联防` 列出「我护着/护着我」；`解除 <称呼/#关系ID>` 结束关系。旧群命令只返回迁移提示，不执行群行为。
- **裸查询**:任意有效用户都可查证；没有联防关系不影响判定。公众号个人身份由首条消息创建，网页仍要求个人 token。
- **网页**:`/` 是个人查询兜底页；`/console` 管理关系、提醒、查询和投票；`/join/{code}` 展示邀请方向与内容共享说明；`/alert/{id}` 展示单条关系提醒与投票状态。
- **跨消息会话**:同一用户查询间隔 ≤6h 并入一案，超时开新案；微信「新的/新问题」显式关案。「谢谢/好的/收到」等确认词只落 `query.kind='ack'` 并回复，不判定、不续案。图片转写回写 `query.transcript`。供给开关默认关闭，现有判定路径保持不变；边界见《家中盾_会话模型_实施规格》。
- **异常与守护**:意外判定故障由 VerificationService 收口为人话兜底回复；进程由 systemd / launchd 单元守护。服务支持多个 worker 共用 Postgres；企微 poller 用 session advisory lock 选主，游标按 kfid 落库，verdict 通过 LISTEN/NOTIFY 触达各 worker 的本地 SSE broker。

## 3. 判定与协同规则

### 3.1 查询提醒
查询受理时将查询者当时活跃的 incoming `guard_relation` 写入 `query_relation`，可为空。判定完成(不论等级,决策 #10)只为该快照中仍活跃的关系各生成一条 alert;扇出由查询事件触发而非判定等级,等级只影响提醒文案(dangerous 高危预警 / suspicious 留意核实 / safe "未发现典型骗术特征")。新关系不补收旧查询。解除后提醒详情与待发送提醒均失权。静音只跳过推送,提醒记录与 SSE 保留。推送带不可变的 `name_at_alert` 快照,不受后续改名影响。

### 3.2 判定回复
`features/judge/annotate/knowledge/reply` 与 incident/triage/supply 判定路径保持原状。ACK、三段式结果和降级提示只返回查询者。查询者仅在实际生成 alert 后收到「已加入提醒列表」说明，不声称模板已经送达；无活跃关系不出现通知声明。

### 3.3 纠正投票
每条 verdict 最多一个 `correction_case`。查询者反馈仅存 `queryer_label/note`，不是投票。dangerous 可由查询者反馈或 alert 接收者开启；safe/suspicious 只能由查询者主动反馈开启。案件打开时冻结投票关系：dangerous 取此刻仍活跃的 alert 关系；低风险取此刻仍活跃的 `query_relation`。每条关系一票，投票者须为关系 protector；固定 N 的严格多数 `floor(N/2)+1` 确认，N=0 立即 `no_consensus`。期限到达后的首次读写收口为 `no_consensus`，期限由 `CORRECTION_WINDOW_DAYS` 配置。解除关系禁止再读内容和投票，已投票仍计入固定分母。仅 confirmed 结果回流，不改写原 verdict、回复或提醒。

### 3.4 隐私
查询回复只回查询者。alert 接收者可看其所收提醒对应的查询内容与判定回复——查询级同步是联防关系内的知情约定，绑定文案明示"你的每次查证都会提醒联防你的人"(决策 #10)。低风险纠正案件开启后，原查询原文向案件投票者开放。无关系的裸查询内容仍只回查询者。关系解除保留外键历史，但即时撤销提醒和案件内容权限。

## 4. 数据模型(Postgres)
在线服务使用 Postgres 16 与 async connection pool；schema 版本由 `schema_version` 记录。时间戳为 `timestamptz`、判定快照为 `jsonb`，迁移脚本仅用于当前关系模型 SQLite 库，不转换旧群模型。离线 `kbbuild` 保留自己的 SQLite 文件。完整业务 DDL 及索引见《关系模型实施规格》§3。

```text
guard_relation(id, protector_user_id, protected_user_id, name, inverse_name,
               mute, created_at, ended_at, end_reason)
invite_code(id, code, creator_user_id, name, created_at, expires_at,
            used_at, used_by_user_id, revoked_at)
query_relation(query_id, relation_id) -- 查询受理时 snapshot
alert(id, verdict_id, relation_id, name_at_alert, delivered_at, read_at)
correction_case(id, verdict_id, queryer_label, queryer_note,
                status, resolved_label, opened_at, closes_at, resolved_at)
correction_vote(case_id, relation_id, label, voted_at) -- 固定合格关系集合
kf_cursor(kfid, cursor, updated_at) -- 企业微信客服账号游标
```

每个 worker 建立独立最多 10 连接的池，连接会话时区固定 UTC，statement timeout 为 5 秒。告警事件由 verdict 事务内 `pg_notify` 发出；各 worker 以专用非池连接 `LISTEN` 并回查 verdict/query 后走相同 `AlertRouter`。通知可能双消费，`alert` 唯一键保证落表幂等；外部企微提醒只由成功新建 alert 的消费方触发。NOTIFY 不持久化，断线期间 SSE 漏收可从告警历史 API 查询。

`(protector_user_id, protected_user_id)` 活跃唯一；不允许自联防。解除只标记 `ended_at/end_reason`，不删历史关系。`query_relation`、alert 与 vote 保留稳定关系 ID；关系双向需要两条单向行，不存在群、租户或工作区容器。

## 5. API 契约
所有个人数据接口由 token 定位 user，缺失或错误 token 返回 401。查询允许零关系；不接受 `group_id`。

| 方法/路径 | 作用 |
|---|---|
| POST `/api/query` | 私人查证，零关系照常判定 |
| GET `/api/relations` | `{guardings, guardians}` 当前关系 |
| GET `/api/join/{code}` | 无 token 的邀请预览，不返回个人凭证 |
| POST/GET `/api/relations/invites` | 创建/列出本人邀请码 |
| DELETE `/api/relations/invites/{id}` | 撤销本人未使用的邀请码 |
| PATCH/DELETE `/api/relations/{rid}` | 修改本人一侧称呼/静音或单方解除 |
| GET `/api/my-queries[/{verdict_id}]` | 本人查询历史、详情与反馈 |
| GET `/api/alerts[?relation_id=]` | 本人作为 protector 收到的提醒；详情 `/api/alerts/{alert_id}` |
| GET/POST `/api/corrections` | 当前有权限的投票队列；查询者反馈或关系投票 |
| GET `/api/stream` | SSE 告警，事件发送前检查关系仍活跃 |
| GET `/console`, `/alert/{alert_id}`, `/join/{code}` | 控制台、提醒详情、邀请落地页 |

解除后的 alert 详情对原接收者返回 410 `relation_ended`，无关者返回 404。周报、群 API、成员管理和信任位已删除。

## 6. 评测规格

**收敛标准(评测纪律,高于本节其余内容)**:
- 唯一的质量收敛标准是**真实世界使用**:真实查询日志、confirmed 纠正(库内留存)、真机/真通道延迟;
- mock、种子样例、合成数据只有两个合法用途:① CI 管道正确性回归;② 冷启动冒烟。**禁止**作为任何质量指标(Recall/FPR/延迟)的收敛与拟合目标——对着自产数据调词表、提示词、阈值,就是"虚假环境陷阱";
- 调整纪律:词表、提示词、阈值、检索权重的每次变更,必须附真实数据复测证据(库内纠正重放或真机日志),否则不合入;
- 报告纪律:`docs/reports/report.md` 强制标注数据来源构成与模式口径;mock 口径的数字只能表述为"管道验证",不得表述为产品质量;
- 配比纪律:§6.1 的样本构成只约束冷启动集 v1;真实使用启动后,数据分布与扩充由真实回流决定,不再按预设配比制造样本。

### 6.1 数据集(`data/samples/`,JSONL,每行一条)
- **规模与构成**:80-100 条;诈骗 40 / 边缘 30 / 正常 30。
- **字段**:`{id, text, label: scam|edge|benign, scam_type(诈骗类才有,对齐分类学), source: "adapted:<出处>"|"synthetic:llm:<model>", notes}`。
- **分层要求**:scam 中 ≥20 条标注 `source=synthetic:llm:*`(由 LLM 生成+人工改写),用于"AI 生成话术检测退化"子评测(中文首发数据点,对标 Frontiers 2026 的英文结论)。
- **边缘档必须覆盖**:真实兼职群、真快递理赔、家人借钱、正常营销短信。
- **来源可溯**:来源与改编方式逐条记录 provenance,防"人造感"质疑。
- **扩展集(候选,不入 v1 主集)**:`data/samples/fraud_r1_base.jsonl`(32 条,8 类均衡,`source=synthetic:llm:deepseek-r1`,**待人工过筛**,已扫描 6/32 含生成残留)与 `data/samples/fraud_r1_levelup.jsonl`(128 条 = 32 案例 × 增强级 0~3 配对,专供"AI 生成话术检测退化曲线");`uv run homeshield-kbcli export-eval` 一条命令复现(§7.3)。

### 6.2 指标定义(公式进 `src/homeshield/eval/run_eval.py` 与报告)
- 检出率 Recall = TP / (TP+FN);TP = 标注 scam 且判为 dangerous+suspicious(dangerous 单列);
- 误报率 FPR = FP / (FP+TN);FP = 标注 benign/edge 且判为 dangerous;
- 分级混淆矩阵(3×3);延迟 P50/P95;分档报告 scam 子集(人工 vs LLM 生成)。

### 6.3 消融矩阵(全部在两种模式下跑)
| 配置 | 特征抽取 | 知识库检索 | LLM 判定约束 | 说明 |
|---|---|---|---|---|
| A(zero-shot) | — | — | 无约束 | 基线 |
| B(A+RAG) | — | ✓ | 无约束 | 检索增益 |
| C(B+约束) | ✓ | ✓ | 引用校验 | 完整方案 |

### 6.4 阈值扫描
判定置信分 → P/R 曲线;工作点按"误报权重高于漏报"选取(产品依据:误报三次=家人拉黑=产品死亡),依据写入报告。

### 7.2 安装与运行(Python 3.12,uv 管理)
- 安装:首次 `uv python pin 3.12` 固定解释器,然后 `uv add openai fastapi "uvicorn[standard]" pydantic python-dotenv httpx`、`uv add --dev pytest`(依赖进 pyproject.toml,锁定 uv.lock,自动创建虚拟环境);`uv sync` 以 editable 方式安装 homeshield 包(`[project.scripts]` 提供三个入口);
- 配置 `.env`:`MODE=llm|mock`;供应商任意命名,每个供应商三件套 `<NAME>_API_KEY / <NAME>_BASE_URL / <NAME>_MODEL`(OpenAI 兼容端点);任务分工 `CHAT_PROVIDER`(判定/补抽/回复)、`TRANSCRIBE_PROVIDER`(图片转写,留空回落 chat)、`EMBED_PROVIDER`(向量检索,留空则纯关键词);
- 运行:`uv run uvicorn homeshield.server:app --reload`;测试:`uv run pytest tests/`;入口:`homeshield-cli`(运维/演示)、`homeshield-kbcli`(离线素材库)、`homeshield-eval`(评测);
- 注意:脚本与测试统一经 `uv run` 执行,不手工 pip install;Python 3.12 下 `match`、`X | Y` 类型联合等新语法可用。

### 7.3 离线素材库(kbbuild,与运行时隔离)
- **定位**:离线批处理资产,服务链路(server/cli/core)永不读取;只有人工审核后的产出物(词表/案例/评测样本)单向进入版本库。
- **数据**:`data/kb_build.db`(`*.db` 已 gitignore):`fr_case`(Fraud-R1 中文语料 4,280 行 = 1,070 案例 × 增强级 0~3,provenance 与许可注记逐行落库)、`fr_tactic_extract`(战术挖掘,预留)、`marker_candidate`(词表审核队列,状态机仿 correction);源文件在 `data/raw/fraud-r1/`(gitignore)。
- **工具**:`uv run homeshield-kbcli init-db|import|stats|export-eval|export-cross-message`(不依赖 .env/LLM,零运行时耦合);`uv run python -m homeshield.eval.run_eval --supply on --mode mock` 做跨消息配对管道评测。

- **红线**:原始语料许可为 HF gated——仅研究/教育用途、不得向第三方转发、不得商用,严禁随产品分发、严禁进公开仓库;评测集并入主集前必须人工过筛(§6.1 扩展集)。
