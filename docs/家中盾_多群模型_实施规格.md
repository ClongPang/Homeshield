# 家中盾 多群模型 实施规格

> 版本:v1.6 | 2026-09-27 | 状态:**开发完成;本地自动化与浏览器验收通过,微信模板实号验证待部署前完成**
> 读者:研发与测试。设计依据:《产品定位》v2.6/决策 #7(机制而非场景)、FR-11;状态同步至《产品定位》v2.7;《架构技术》v2.25。
> 判定契约:features/judge/annotate/knowledge 的风险判断与三段式结构不变;`reply.py` 去掉与实际告警无关的固定"已通知家人"后缀,送达说明由协同层按告警生成结果补充。

## 1. 目标与不变式

**目标**:一个微信号可加入多个防护群;单群用户沿用原查询与通知路径,并纠正原有"未通知却说已通知"的文案。

四条不变式,所有实现决策用它裁决:

| # | 不变式 | 含义 |
|---|---|---|
| I1 | 查询私人 | 回执、判定回复、降级提示只回到查询者自己的对话,不进群 |
| I2 | 告警广播 | 查询受理时固定相关群;dangerous 判定时向这些群仍活跃的已绑定成员生成告警,模板按用户去重;新加入的群不接收旧查询 |
| I3 | 单群零感知 | 只有一个活跃群的用户:查询流程、三段式结构、模板字段和交互与当前版本一致;群选择器与带群名模板只面向多群用户 |
| I4 | 一次操作 | 查询、打开告警、提交纠正均不要求选群;控制台只有进入按群页面时才显示明确的群上下文 |

**反屎山纪律**:不写旧库迁移层(dev 库重建);不引入通用租户框架;不实现本规格未列的功能;每个便捷项必须能一句话说清"省掉了用户的哪一步"。

## 2. 范围

### 2.1 做(P1→P3)
1. 身份与成员关系分离:`user` 表(一个微信号一行)× `member` 表(收窄为成员关系:某用户在某群);
2. 多群命令:`开通 [群名]`、`我的群`、`退出 <群名/序号>`、创建者`解散 <群名/序号>`;
3. 告警广播:查询时相关群快照、判定时活跃成员扇出、按用户去重、按接收者选模板;
4. 控制台群切换器 + 按 `group_id` 的群上下文;
5. 移除成员 / 退群 / 创建者解散群(补既有缺口),最后信任成员护栏与历史保留;
6. 便捷项:邀请链接落地页、群改名、成员自改昵称、per 群静音、控制台新建群。

### 2.2 不做(明确出范围)
| 不做 | 原因 |
|---|---|
| 切换群命令 / 默认群设置 | 告警广播使归属选择不存在;消灭选择优于管理选择 |
| @群名消息语法 | 同上;语法是摩擦不是能力 |
| 旧库迁移兼容层 | dev 库重建;生产部署前仅建新 schema |
| 通用租户/工作区框架 | 只做 user × membership,不做抽象插件 |
| 群 OAuth 直通入群、免打扰时段 | 观察项,真实使用数据裁决后再评估 |

## 3. 数据模型(DDL,一次性重建 dev 库)

```sql
CREATE TABLE user(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    openid TEXT UNIQUE NOT NULL,     -- 真实用户=微信 openid;演示/测试使用保留的 demo:/test: 前缀
    token  TEXT UNIQUE NOT NULL,     -- 控制台"链接即凭证"(用户级,不随群)
    created_at INTEGER NOT NULL
);

CREATE TABLE protection_group(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    created_by_user_id INTEGER NULL REFERENCES user(id), -- 微信自助建群的创建者;CLI 空群可为 NULL
    created_at INTEGER NOT NULL,
    disbanded_at INTEGER NULL        -- 解散时间;NULL=活跃
);

CREATE TABLE member(                 -- 语义=成员关系:某用户在某群
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    group_id INTEGER NOT NULL REFERENCES protection_group(id),
    user_id  INTEGER NULL REFERENCES user(id),   -- NULL=未绑定的成员位(邀请中)
    name TEXT NOT NULL,              -- 群内昵称(同一人在不同群可不同)
    trusted INTEGER NOT NULL DEFAULT 0,          -- 本群纠正信任位
    mute INTEGER NOT NULL DEFAULT 0,             -- 本群推送静音(仅静模板推送)
    created_at INTEGER NOT NULL,
    ended_at INTEGER NULL,           -- NULL=活跃;终止后留行供历史记录引用
    end_reason TEXT NULL CHECK(end_reason IN ('left','removed','disbanded')),
    CHECK((ended_at IS NULL) = (end_reason IS NULL))
);
CREATE UNIQUE INDEX uq_active_member ON member(group_id, user_id)
    WHERE user_id IS NOT NULL AND ended_at IS NULL;

CREATE TABLE bind_code(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL UNIQUE,
    member_id INTEGER NOT NULL REFERENCES member(id),
    created_by INTEGER NULL REFERENCES member(id),
    created_at INTEGER NOT NULL,
    expires_at INTEGER NOT NULL,
    used_at INTEGER NULL
);
CREATE TABLE query(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES user(id),
    content_type TEXT NOT NULL CHECK(content_type IN ('text','url','image')),
    content TEXT NOT NULL,
    msg_id TEXT NULL,
    created_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX uq_query_msg_id ON query(msg_id) WHERE msg_id IS NOT NULL;
CREATE TABLE query_group(
    query_id INTEGER NOT NULL REFERENCES query(id),
    group_id INTEGER NOT NULL REFERENCES protection_group(id),
    query_member_id INTEGER NOT NULL REFERENCES member(id),
    PRIMARY KEY(query_id, group_id)
);
CREATE TABLE verdict(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    query_id INTEGER NOT NULL REFERENCES query(id),
    level TEXT NOT NULL CHECK(level IN ('safe','suspicious','dangerous')),
    cited_ids TEXT NOT NULL,
    features TEXT NOT NULL,
    reason TEXT NOT NULL,
    reply TEXT NOT NULL,
    latency_ms INTEGER NOT NULL,
    mode TEXT NOT NULL CHECK(mode IN ('mock','llm')),
    created_at INTEGER NOT NULL
);
CREATE TABLE alert(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL REFERENCES verdict(id),
    membership_id INTEGER NOT NULL REFERENCES member(id),
    group_name_at_alert TEXT NOT NULL,
    delivered_at INTEGER NOT NULL,   -- 告警生成时间,不表示微信模板送达成功
    read_at INTEGER NULL,
    UNIQUE(verdict_id, membership_id)
);
CREATE TABLE correction(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    verdict_id INTEGER NOT NULL REFERENCES verdict(id),
    by_user_id INTEGER NOT NULL REFERENCES user(id),
    label TEXT NOT NULL CHECK(label IN ('real','false_positive')),
    note TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL CHECK(status IN ('pending','confirmed','rejected')),
    decided_by_membership_id INTEGER NULL REFERENCES member(id),
    created_at INTEGER NOT NULL,
    decided_at INTEGER NULL,
    UNIQUE(verdict_id, by_user_id)
);
CREATE TABLE correction_group(
    correction_id INTEGER NOT NULL REFERENCES correction(id),
    group_id INTEGER NOT NULL REFERENCES protection_group(id),
    by_membership_id INTEGER NOT NULL REFERENCES member(id),
    PRIMARY KEY(correction_id, group_id)
);
```

**约束与口径**
- 活跃关系 = `member.ended_at IS NULL` 且 `group.disbanded_at IS NULL`;群列表、成员数/用户群数限制、入群和鉴权均只看活跃关系/活跃群。服务级群数不设上限。未绑定成员位(`user_id=NULL`)可并存,不算作"已绑定成员"或信任护栏人数;
- 部分唯一索引保证同群同用户最多一条活跃关系;退出/移除后保留旧 `member.id/user_id` 及其外键引用,再次绑定入同群创建**新**成员关系,不得复活旧行;
- 正式用户经微信绑定/开通产生;CLI `add-member` 不带 `--openid` 只建未绑定邀请位,没有个人 token;带真实 `--openid` 时 find-or-create user。演示专用 `--demo-user` 创建 `demo:` 前缀的唯一合成身份并发个人链接,绝不向微信推送;测试夹具使用 `test:` 前缀合成身份,替代 token-only member;
- 接收查询时,在同一写事务内插入 `query` 与全部 `query_group`;以后入群/退群/改名均不改这份相关群快照。判定时只在快照群中选择**仍活跃的群和已绑定成员关系**生成 alert;查询者判定前退群则不再作为该群接收者,其他仍在群里的成员照常收到;判定前新加入的群不接收这条查询;
- `query_group` 同时用于每群周报的查询数。原 `query.group_id`/`query.member_id` 单群归属与"最早加入群"记账口径取消;同一查询属于当时查询者所在的每一个群,各群周报可各计一次,跨群相加可能重复;
- 应用层在写入时校验 `query_group.query_member_id` 属于该 `group_id` 与 `query.user_id`,`correction_group.by_membership_id` 属于该 `group_id` 与 `correction.by_user_id`,且当时关系活跃;写入后这些引用不随退群更改;
- alert 只写判定时活跃且已绑定的成员位;未绑定邀请位不收告警。`group_name_at_alert` 记录判定时群名,群后续改名不改历史告警文案;模板发送前复核接收者至少仍有一个相关、未静音的活跃成员关系;
- `correction` 按 `verdict_id × user_id` 唯一,同一人无论兼任几群只反馈一次。dangerous 的有权反馈群=该用户当时收到 alert 的群 ∩ 当前活跃群;safe/suspicious 仅原查询者可反馈,有权反馈群=`query_group` ∩ 当前活跃群。提交时每个有权反馈群写一条 `correction_group` 并保留当前 `by_membership_id`;任一群当前可信则直接 confirmed,否则 pending,由这些群任一活跃信任成员确认一次,状态全局同步;`decided_by_membership_id` 保留裁决时的成员关系;
- 信任成员提交即 confirmed 时,`decided_at=created_at`,有多个可信群时以 `member.id` 最小的可信成员关系记入 `decided_by_membership_id`;pending 裁决时写入裁决时间和裁决者成员关系。周报按 confirmed 的 `decided_at` 归入统计期;
- 退群/移除/解散均**不 DELETE member**、不清空历史 `user_id`;`query_group/alert/correction_group/decided_by_membership_id/bind_code` 的成员关系外键仍指向历史行。未使用邀请码作废(沿用 `bind_code.used_at` 失效机制),历史行保留;
- 解散群置 `disbanded_at`,把包括未绑定邀请位在内的全部活跃 `member` 标为 `ended_at/end_reason='disbanded'`;历史数据仅供后台审计,家人 API 无该群访问入口。`MAX_GROUPS` 统计用户当前加入的未解散群,创建群和邀请码入群都会检查。

## 4. 微信命令与消息

### 4.1 命令
| 命令 | 行为 | 护栏/文案 |
|---|---|---|
| `开通 [群名]` | 无群:建群,创建者即群主(trusted);已有群且未带名:回当前群列表 + 提示"新建群请回复:开通 群名";带名:建新群 | 用户的活跃群数受 `MAX_GROUPS` 限制;服务级群数不设上限 |
| `绑定 <码>` | 不变;落位时 find-or-create user(一人入多群的通道) | 同群活跃关系唯一;已解散群/已终止成员位的码无效 |
| `我的群` | 列出真实所在群:`1. 妈妈家(信任) 2. 岳父家(普通)`;无默认群/记账群标记 | — |
| `退出 <群名/序号>` | 终止本人成员关系;仍有其他已绑定成员时执行最后信任成员护栏;最后一名已绑定成员退出→群自动解散 | 需转移信任时提示先设置信任成员 |
| `解散 <群名/序号>` | 仅仍在群内且为信任成员的创建者可主动解散;立即终止全群成员关系并作废邀请码 | 其他人无权解散;其余群不受影响 |
| 其余文本(不在任何群) | user 存在但**零活跃成员关系**(全部退出/所在群解散):回复"你当前不在任何防护群中。回复「开通 [群名]」新建,或请群主发邀请码";此状态裸「开通」直接建群,无歧义 | 覆盖"从未加入"与"曾加入已全部退出"两种来源,`BIND_GUIDE` 文案按此更新 |
| 其余文本(在群) | = 查询,走既有管线 | — |

### 4.2 查询者消息(不变式 I1/I3/I4)
- 不论所在群数,回执仍为`收到,正在帮你看…`,判定回复仍为原三段式,降级提示仍为原文案;不加 `【群名】` 前缀,不要求选择群。用户只需转发或发送可疑内容;`safe/suspicious` 或 dangerous 但未生成任何告警时,不得出现"已经告诉家人"之类的已通知表述;
- 查询受理时在多个群的用户,遇到 dangerous 判定时在原回复之后补一条**仅查询者可见**的说明,列出本次实际生成告警的群,例如`已向妈妈家、岳父家发出高危提醒`;查询受理时只有一个群且生成告警的用户沿用现有单群提醒文案。没有任何活跃群可接收时,说明本次未通知群成员;文案依据 alert 落行结果产生,不将模板投递成功与否混作已读;
- 群名只出现在多群接收者的模板、告警详情及控制台群上下文中;判定回复不以某个群名暗示查询只归属那一群。

### 4.3 模板消息
- 保留现有单群模板及其 `WECHAT_TEMPLATE_ID`:字段仍为 `thing1`(摘要 ≤20 字)、`phrase1`(高危预警),不增加群名。另配置 `WECHAT_MULTI_TEMPLATE_ID` 对应带 `thing2`(相关群名)的多群模板;按**接收者发送时的活跃群数**选模板,不是按查询者群数;
- 每个 `verdict_id × user_id` 最多发送一条微信模板。对该接收者取本次 alert 涉及、发送时仍活跃且 `mute=0` 的群作为**推送群集合**;集合为空则不推送。多群模板有一个推送群时写该群名,多个时写`妈妈家等2群`之类的短摘要,详情页列出全部相关群;按 `protection_group.id` 升序选摘要中的首群,过长群名按所配模板字段上限截断,不改变计数;
- `mute=1` 只关闭该群导致的微信模板:alert 历史和 SSE 仍保留;同一人兼任静音群 A 与非静音群 B 且本次事件涉及两群时,仍收一条通知,模板只写 B。发送前复核群及成员关系仍活跃,离群后排队中的模板不再发送;
- 两套模板的 ID、字段与落地页链接须在测试号/服务号上验证;仅配置旧模板时不得把多群消息塞进旧模板,部署前补齐多群模板配置。

## 5. API 契约

### 5.1 上下文规则
- token 定位 **user**。查询/纠正提交/告警详情无需 `group_id`;告警列表、待确认队列、周报等按群页面要求明确群上下文:仅有一个活跃群时可省略 `group_id`,有多个活跃群时必须传 `group_id`。控制台优先恢复上次查看且仍活跃的群,否则展示群选择器;所选群名始终在页面标题可见;
- 已有 user 但零活跃群时,`GET /api/groups` 返回空列表,控制台显示`你还没有加入防护群`及开通/绑定指引;`POST /api/groups` 仍可新建群,`POST /api/query` 返回明确的未入群错误,不进入判定管线;
- 访问控制:任何群数据接口要求 user 在未解散群拥有活跃成员关系,否则 404;退群/移除后旧 token 仍定位 user,但不再授予原群访问权;重新入群按新关系授权;
- 告警列表与详情按 `alert.membership_id → member.group_id/user_id` 授权:当前仍在相关群,且该用户在判定时曾有该告警的接收成员关系,才能查看;退出后失权,重新加入原群可恢复自己当时收到的历史告警,但不能看离群期间或首次入群前产生的告警。原查询者退出不影响当时其他接收者打开自己的告警;解散群的历史仅供后台审计;
- 旧告警链接由原接收者打开时,若只是退群或群已解散,落地页分别显示`你已不在这个防护群，暂时无法查看这条提醒`、`该防护群已解散，历史提醒无法查看`;无从证明其曾收到该告警的请求仍返回普通 404,不泄露记录;
- SSE 对同一 `verdict_id × user_id` 只送一个事件,payload 带其相关 `group_ids/group_names`;在送出前重新校验当前活跃成员关系,退群/解散后不再送该群事件;加入新群后控制台重连流。前端按所选 `group_id` 过滤,同一判定不显示重复卡片;
- dangerous 纠正入口只对曾收到该判定 alert 且目前仍在至少一个接收群的用户开放;safe/suspicious 的私有判定只允许原查询者纠正,并要求其仍在当时的至少一个相关群。提交时服务端按 §3 的规则确定有权反馈群并写 `correction_group`,不要求用户选群;任一有权反馈群当前为信任成员则直接 confirmed,否则 pending。`pending` 反馈会把原查询内容展示给其有权反馈群的信任成员,按钮旁说明这一点,不增加确认步骤;这些群中任何活跃信任成员可裁决一次,pending 在所有相关群队列中同步消失;无交集者无法提交/裁决;
- 每群周报:`queries`=本群 `query_group` 中在统计期内受理的查询数;`dangerous`=本群在统计期内生成过 alert 的不同判定数;`corrections`=本群 `correction_group` 中统计期内变为 confirmed 的纠正数;`false_positives`=其中 label 为 false_positive 的数。pending/rejected 不进统计;按 `query.id`/`verdict.id`/`correction.id` 去重,不把多个群的数字相加宣称为全局总量。

### 5.2 接口
| 方法/路径 | 说明 | 变更类型 |
|---|---|---|
| GET `/api/groups` | 我的群列表 `{groups:[{id,name,trusted,member_count}]}`,不返回 `is_default` | **新增** |
| POST `/api/groups` | `{name}` 新建群,调用者成为群主 | **新增** |
| PATCH `/api/groups/{gid}` | 群改名,仅该群信任成员 | **新增** |
| DELETE `/api/groups/{gid}` | 创建者主动解散;须仍在群内且为信任成员;全群关系终止、邀请码作废 | **新增** |
| GET `/api/stream` | SSE;每人每判定至多一个事件,payload 含 `group_ids/group_names` | 改 |
| GET `/api/alerts` | 按 `group_id` 查本人当时收到、且目前仍有权查看的告警;多群必传 `group_id` | 改 |
| GET `/api/alerts/{id}` | 仅当前活跃相关群中,本人当时收到过的 dangerous 告警;详情列出本人仍可访问的相关群;原接收者失权返回 410 与 `membership_ended/group_disbanded` 原因码,其他无权者 404 | 改(鉴权口径) |

### 5.3 成员关系终止与解散(三条路径共用)
- 不变式:**未解散且仍有已绑定成员的群,至少有一名活跃、已绑定的信任成员**;未绑定邀请位不能满足护栏,也不能被提升为信任成员;
- `退出`/`移除`:若退出后仍有已绑定成员,且将失去最后一名活跃信任成员,则原子拒绝并提示先转移信任;若退出者是最后一名已绑定成员,同一事务内自动解散,终止剩余未绑定邀请位;
- 创建者主动解散:以 `group.created_by_user_id` 验证创建者身份,另要求其仍是活跃信任成员;即使还有其他成员也可解散,因为群直接变为非活跃,不套用"活跃群至少一名信任成员"护栏;
- 三条路径在单个 SQLite 写事务内校验、更新 `ended_at/end_reason` 与 `group.disbanded_at`、作废未使用邀请码;并发退群/移除/降级不能留下有成员却无信任成员的活跃群。共享连接上的**全部仓储数据库访问**(读与写)共用进程内 `threading.RLock`;多进程部署须改为每请求独立连接及数据库级写事务,不得让跨进程写入绕过锁;
- CLI 建的群 `created_by_user_id` 为 NULL,无法走创建者解散:提供 `homeshield-cli disband --group-id` 运维子命令兜底(同等护栏与历史保留口径);
- 群终止后 user 与其 token 均保留;若用户仍在别的群,那里的成员关系与历史不受影响。重复退出/解散不再次改变历史行。

## 9. 风险与观察项
